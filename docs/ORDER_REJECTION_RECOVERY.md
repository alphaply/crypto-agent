# 交易所拒单后遗留的“提交中”记录

`client:...` 是提交前生成的本地引用，不证明交易所有这张订单。只有交易所返回的订单号才可用于改单、撤单。没有订单号的本地记录不再展示可撤单、可改单，也不允许把 `client:` 引用发往交易所。

币安 `-4130` 表示同方向已有全仓条件退出单，因此拒绝再创建该订单；`-1102` 表示请求参数缺失或格式错误。CCXT 4.5.34 将前者作为 `ExchangeError`、后者作为 `BadRequest` 抛出。旧提交代码只捕获部分异常子类，导致这些明确拒单错误被记成 `unknown`，本地记录一直保留 `submitting`。

修复后，独立退出模式在提交阶段按已有的交易所拒绝码识别失败，不再依赖这几个异常子类。明确失败仅结束本次操作；下一次明确动作仍按当前持仓、目标和订单事实检查。

历史记录在正常加载和后台核验时自动纠正：记录必须仍为未确认提交或拒绝、没有交易所订单号或受理/触发/成交证据，且原始提交的 `execution_error` 含明确拒绝码。符合条件的记录变为 `rejected` / `not_submitted`，不再作为活跃挂单或未决阻塞项；原始错误、操作身份、核验次数和历史回执保留。此前由失败核验留下的重试与待核验标记清除。

撤单、查询报错和“挂单列表没有这张单”不能替代原始提交结果。超时、重复客户端编号、已经受理或成交的记录继续按原身份处理，不通过删除记录或补填成交解除。修复不会重放交易、补发未执行动作或主动撤单。

工具说明中的 `pending/unknown` 停止范围为本轮后续交易。以后的决策应结合当前账户事实和具体动作的准入结果，不能从历史未决记录推断整个账户永久停用；依赖未决操作的动作仍须等待对应事实明确。

本修复不需要数据库结构迁移。Web 和 scheduler 更新到同一版本后，由正常后台处理纠正符合条件的旧记录。检查原操作最新回执为 `failed`、对应记录不再出现在当前挂单和未决阻塞项中；保留原始回执用于追溯。仅发布镜像不会更新正在运行的生产实例。
