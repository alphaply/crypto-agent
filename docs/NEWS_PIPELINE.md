# 消息流水线与触发配置

配置入口：**配置 → 消息聚合**。模型渠道和密钥在「模型与价格」管理，律动 API Key 在消息聚合单独保存。抓取、评分、摘要模型与交易模型独立。已有配置继续默认使用 Jev，不自动切换评分方式或开启自动交易。

## 输入、过程和输出

1. 输入：律动 JSON API、RSS、政策新闻、宏观日历、Polymarket、币安公告流。保存标题、正文、来源、URL、发布时间/预定时间。日历只有预告，不能提供尚未公布的 CPI 实际值；需从报道数据公布值的消息源获取。
2. 采集：并发获取，按消息窗口过滤，去重，截取 `candidate_limit`。源故障可回退缓存并标明过期。消息原文始终作为数据，不能改变系统指令。
3. 可选评分：`off` 不调用评分模型、不伪造分数，按发布时间选取；`jev` 使用 TypeSafe/B.AI；`llm` 用普通生成模型每批最多 20 条评分，严格核验每条 ID 与 0–100 分。相同内容、模型与标准的成功结果使用缓存，失败不会缓存成低分。宏观 CPI、就业、利率属于相关信息，不要求出现加密货币关键词。
4. **触发观察独立发布**：保存候选新闻及可用评分，不受摘要入选数、摘要阈值或摘要调用失败影响。任务触发规则拥有自己的阈值。全部评分失败则不发布新观察；关闭评分时不受评分服务影响。
5. 筛选：评分开启时应用 `min_score`，最多选 `max_items` 条；关闭评分时只按时间与数量筛选。
6. 摘要：`rolling` 将旧摘要及其时间，与**当前入选原文**交给普通 LLM，合并重复、修正冲突、移除过期内容、重新编号引用；`full` 只使用当前原文。没有仅凭旧摘要反复递归，避免错误累积。当前原文仍会带入，因此滚动模式不保证每次输入 token 比全量更少。
7. 输出：统一 `digest`、入选原文与引用、宏观/加密标题、日历、概率信息、来源健康与时间。Agent、Chat、Dashboard 和 MCP 读取快照，不各自重复采集/评分。`as_of` 是采集快照时间，`summary_as_of` 是摘要实际生成时间；`summary_reused`、`summary_deferred` 区分复用与等待。

输入不变跳过摘要调用。输入变化但未到 `summary_min_seconds` 时，保留旧摘要**连同旧引用**，新消息仍可触发任务。改变模型、摘要要求、评分方式、窗口或阈值会重新生成。过期内容或空窗口不继续保留旧摘要。每轮失败仍保留上次成功快照并显示失败原因。

## 时效和费用配置示例

- 评分：先选 **关闭评分**，观察 CPI 等宏观覆盖；需要过滤时选普通 LLM，配置包含宏观信息的评分标准。相关度不是价格预测或交易置信度。
- 抓取间隔：1 分钟；摘要最小间隔：5–15 分钟；候选 80 条、摘要 20 条起步。无变化只抓取，不重复生成摘要；源 API 自身的配额仍适用。
- 开启「币安推送加速刷新」后，有新公告可打断小时抓取周期，最短 1 分钟再采集；币安流必须正常连接。其他来源仍轮询。
- 调度器每分钟检查，抓取/评分完成后，额外 Agent 在后续调度检查启动。端到端还包含源站延迟及模型耗时，**不是秒级推送保证**。常见情况下需一个或两个调度周期，失败重试会更久。
- 摘要等待不阻塞触发观察。降低候选数量、关闭评分、批量评分和摘要复用可以降低模型开销。每次已触发 Agent 仍可能包含多轮模型/工具调用；每日次数不是金额预算。

## 消息触发 Agent

在「消息触发 Agent」选择任务，再指定本次触发专用模型。可在模型渠道添加任意兼容供应商，例如自己渠道中提供的低价 DeepSeek/Flash 类模型，使用该渠道**实际可用的模型 ID**。名称不硬编码，也不替用户更换渠道。

- 默认关闭，必须主动启用。来源、类别、关键词、可选评分阈值之间为 AND；同组列表值为 OR。列表为空表示不限制该项，但至少需一个条件。
- CPI 示例：关键词 `CPI`、`通胀`，新闻最长时效 10 分钟，冷却 30 分钟，每日最多 4 次；若关闭评分，最低相关度留空。模型选已保存的低价工具调用模型。
- 首次启用/编辑规则先建立当前新闻基线，避免把历史消息突然拿去交易。重启后持久化去重仍有效。过期、未来时间、无发布时间、日历预告、来源回退缓存不触发。
- 同一轮匹配新闻合并执行，最多附带 20 条；触发模型只覆盖该次执行，沿用任务交易权限、风控和账户，不使用原任务的昂贵回退链。任务常规定时运行的模型不变。
- 正在运行、同分钟常规定时运行、冷却期、每日次数上限均抑制额外运行；被抑制消息消耗去重标记，不在冷却结束后重放。固定现货定投 `SPOT_DCA` 和外部 MCP 管理任务不额外触发，避免突破定投时间计划。
- 每日以 UTC 日计数。预算在入队前预留；入队失败/崩溃也可能消耗一次，优先避免重复交易。页面显示检查状态、已预留次数与日期。启用总交易调度和该任务后才执行；全局消息抓取本身不受交易调度关闭影响。

## LangSmith 配额

「运行配置」中保留全局 LangSmith 开关，Agent 交易决策及聊天保留完整追踪。辅助摘要、记忆调用的远程追踪默认关闭，可独立打开。消息聚合默认 `off`，本地调用/费用审计仍在；排障时可选：

| news.trace_mode | 上传内容 |
| --- | --- |
| off | 不上传消息流水线及其模型调用 |
| summary | 每次刷新一条根概要，包含耗时、状态和计数，无逐条子运行 |
| full | 根运行、来源、Jev 调用、摘要及模型子运行 |

不要为了节约消息采集追踪而对全部 Agent 随机采样。使用 SDK 的按执行上下文控制，避免并发任务互相切换全局开关，参见 [LangSmith 上下文控制](https://reference.langchain.com/python/langsmith/run_helpers/tracing_context)。

本地处理历史仍保留 20 轮、费用记录独立保留。每分钟刷新若开启概要，一天就会产生约 1,440 条消息根运行；如果只关心 Agent，消息模式应选 off。这里限制的是应用发送行为，不承诺账户额度一定不超：不同套餐的 trace/span 计费口径及 Agent 工具调用量应以自己的控制台为准。
