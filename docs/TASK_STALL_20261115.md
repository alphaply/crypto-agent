# 任务长期停在 preparing 的排查与修复

2026-11-15 线上只读检查确认：ETH 实盘任务的 2026-11-14 23:30 轮次停在 preparing，
到次日 15:33 已有 32 轮等待；现货任务的 04:00 轮次也停在 preparing。
调度器仍登记新轮次，但没有继续输出 AgentGraph 的开始分析日志。
公网健康接口与 MCP 授权查询成功，不能据此推断交易执行链路正常。

本地确定性复现发现：交易所连接包含循环引用，Python 回收旧连接时会调用账户引用释放回调。
如果此时正持有账户协调锁创建新连接，回调再次获取同一普通锁，会永久等待，且不抛出异常。
改为可重入锁后，相同复现正常结束。资源诊断也不再嵌套持有账户锁和行情目录锁，
避免与连接清理形成相反的锁顺序。回归用例在独立子进程验证，失败时保留线程栈并有界退出。
随后通过服务器 py-spy 只读采集确认，本次线上根因就是该锁重入：
resource-evidence 线程停在 `_release_account → weakref.finalize → catalogue_diagnostics → diagnostics`，
两个 agent-job 线程均停在 `start_node → MarketTool → install_transport → retire_runtime_caches`。
成交同步、持仓维护和行情目录工作线程也被同一锁链阻塞。主调度循环仍正常登记任务，
因此健康检查成功、队列继续增长，但策略无法开始执行。Web 的当次采样没有相同死锁，
MCP 授权和现货余额只读检查成功；不能把用户此前的每次 MCP 断连都归因于这一现场。

任务连续 10 分钟没有进度更新时，执行面板显示“任务长时间无进展，可能已卡住”，
显示无进展分钟数，保留原阶段和真实 RUNNING 状态。调度器每分钟检查正在执行的任务，
每个卡住任务每 10 分钟最多记录一次 TaskStalled 错误，包含阶段及调用栈位置，
不记录函数参数、局部变量或凭据。正常进度恢复后按新的进度时间判断。

告警不强杀线程、不提前释放交易锁或并发名额、不重复提交原轮次。
更新 Web 和 scheduler 后生效，无数据库迁移。已卡死的旧进程不会因发布镜像自动恢复；
按 [部署指南](DEPLOYMENT_GUIDE.md) 更新应用并核对后续轮次。
既有重启恢复逻辑将已经开始的旧轮次标为 INTERRUPTED，保留尚未开始的排队项，
按顺序读取最新行情和账户执行。不要手动把 RUNNING 改成 QUEUED 或清除交易账本。
