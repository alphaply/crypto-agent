# 工具调用排查与界面

模型在正文里写出 JSON、工具名或“已执行”，都不能证明操作发生。实际调用以 `tool_calls` 和工具回执为准；已提交也不等于已成交。

## 先区分三种情况

| 现象 | 能确定的事实 | 下一步 |
| --- | --- | --- |
| 请求报 401、429、503 或超时 | 本次模型请求失败 | 检查凭据、额度或服务商可用性；不要据此推断模型不支持工具 |
| 正常返回正文，工具调用为 0 | 模型本轮没有发出实际调用 | 检查正文的等待理由、未决订单状态、请求是否携带工具；JSON 文本不是调用 |
| 有工具调用，但回执失败或待核验 | 已进入工具处理阶段，结果需按回执判断 | 核对参数、权限和原操作证据，不重复提交结果未知的交易 |

2026-11-12 的只读排查中，线上 ETH Argon 10:30 记录正常结束（`finish_reason=stop`），工具目录有 4 项，`tool_calls=[]`。模型在正文中明确因已有“提交中、事实待核验”订单而选择暂停后续交易。这一记录不能归因于 API 不支持工具，也不应靠强制调用或清除未决记录来绕过。

同日使用本地保存的旧 B.AI 凭据进行独立探测，带工具的流式、非流式请求和不带工具的普通请求均返回 HTTP 503 / `model_temporarily_unavailable`。该结果仅代表这组凭据和请求当时的通路，不代表线上当前渠道全部不可用，不能用它解释之前已经正常返回的记录。

B.AI 的 [Argon 说明](https://docs.b.ai/llmservice/models/gemini-4-argon/) 列出 function calling，并注明可用能力取决于端点；[接口文档](https://docs.b.ai/llmservice/api/) 定义不同端点的兼容范围。不要仅凭模型名推断某个渠道的实际行为。

## 新界面如何显示

- 使用白色卡片、浅灰背景和蓝色执行提示，沿用现有主题与布局。
- 模型生成参数、等待执行、执行中分别显示；真实回执到达后，展示各项结果。没有回执的历史调用显示“未收到结果”，不自动标成成功。
- “本轮未调用工具”可展开查看发送工具数量、返回调用数量、选择方式和结束原因。旧记录未保存这些字段时明确说明无法判断接口能力。
- 较长的模型 JSON 默认折叠并标注“仅文本”；内容不转成可执行操作。
- 历史文本回执显示工具名称、原文和独立详情入口；不从自然语言猜测结构化成功状态。
- 聊天收到参数片段时显示“正在生成工具参数”；仅在审批通过且进入执行路径后显示“执行中”。结果事件保留工具名称和调用 ID，以匹配原参数。

诊断信息附在既有 `reasoning_diagnostics` 中，覆盖最终请求的 `extra_body` 设置。新增字段仅包含工具数量、选择模式、调用计数及结束原因，不保存 API Key、工具参数或 schema。诊断不会增加模型请求，也不会触发重试或强制交易。提示词追加执行约定，允许正常等待；用户自定义文件保持原样。

## 无交易动作的接口探测

在配置相同模型凭据的环境中运行：

```powershell
uv run python scripts/check-tool-calling.py --provider-id <已保存的模型配置ID>
```

也可在环境变量 `BAI_API_KEY` 已安全设置时指定端点与模型：

```powershell
uv run python scripts/check-tool-calling.py --base-url https://api.b.ai/v1 --model gemini-4-argon
```

脚本最多发送 4 个小请求，比较流式/非流式和 `auto`/`required`，会产生正常模型调用费用。仅提供无实际实现的 `diagnostic_echo` 函数，**不执行返回的调用，不加载交易工具，不读取交易账户**；遇到请求失败即停止后续探测。`required` 只用于该诊断，不用于真实交易。输出不含凭据或原始请求/响应正文。

如果探测成功，只证明该通路能够返回简单函数调用；不能保证复杂真实交易决策每次都会调用工具。如果返回 503，待服务恢复后再测，不自动切换其他服务商。
