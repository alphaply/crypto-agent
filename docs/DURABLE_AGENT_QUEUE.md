# Agent 持久排队

定时策略、合格新闻触发与现货定投先保存到 PostgreSQL `agent_run_queue`，获得运行名额后才开始分析。忙碌时保留所有不同触发，不按等待时间丢弃，也不合并。重复读取同一触发身份不会增加一轮。

同一任务依次执行。若 A 正在运行，队列是 A、B，而仍有空闲名额，B 可以先开始，等待中的 A 保留。队列按条领取，积压不变成内存中的大量 Future，也不占用正在运行的额度。`SCHEDULER_MAX_WORKERS` 和现有进程并发设置继续控制实际运行数量；现有交易所限流及请求超时保留。

每个已入队的定投时槽保留原 UTC 周期身份。三个各 100 USDT 的时槽会分别执行三轮，最多可能合计使用 300 USDT，仍受真实余额与任务总预算约束。同一时槽重试不会生成另一份额度。运行时采用最新的金额、模型和策略参数，并重新获取行情及账户事实。

新闻在入队时判断原有过滤条件、冷却时间与每日次数；事件身份、已预留次数和队列项同事务保存。合格新闻与同分钟普通计划分别入队。等待不会再次扣次数，也不会把原新闻改写成最新发布的消息；模型看到原消息及其时间。

暂停任务或全局调度会取消未开始项。删除任务以及账户、交易所、品种或交易模式变化也取消未开始旧项。更改模型、策略参数、金额不取消队列，开始时读取最新值。取消排队不撤交易所订单，也不清除已提交操作的恢复证据。

重启后未开始项继续排队。已开始而中断的轮次标记 `INTERRUPTED`，不重新调用模型整轮下单；已尝试交易继续由现有后台按原操作及订单身份核验。旧版本未完成且没有可靠启动边界的调度记录同样标记中断，不猜测其是否已经下单。本次没有增加停机期间未受理时槽的批量回填。

运行仍采用同宿主 Web 与唯一 scheduler，二者共享 `DATA_DIR`。scheduler 持有共享目录中的进程生命周期锁，避免另一进程错误地把仍在执行的工作判成中断。PostgreSQL 用短事务领取队列并保证同一任务只有一个已领取或运行项。

页面通过批量接口分别获取 `running`、`queued_count`、`next_queued`、`last_run`，新排队项不会覆盖正在运行的进度。数据库迁移为 `0010_durable_agent_queue.sql`，仅新增队列及触发标识，不重写既有交易身份。

本次只执行了隔离 PostgreSQL、假模型/假交易入口的聚焦测试；完整回归与实际部署验证仍由用户完成。
