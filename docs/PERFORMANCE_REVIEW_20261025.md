# 加载性能与 Paper 估值检查（2026-10-25）

本次针对页面加载、看板查询、模拟交易分页和“估值不完整”进行代码检查与修复。证据来自本地构建、隔离数据库测试与模拟接口浏览器检查；没有据此声称生产服务器的响应时间已经下降，也没有修改线上账户。

## 已确认的问题与改动

| 位置 | 原因 | 处理方式与影响 |
| --- | --- | --- |
| 首页 | 图表和共享消息的 Markdown 组件进入页面静态依赖，开始获取页面数据前就要加载 | 组件实际显示时再加载；图表保留固定高度占位，数据请求可更早开始 |
| 配置页 | 为显示记忆面板静态引入整个工作区；多个配置区块提前加载 | 将相关组件改成按需加载，减少进入配置页时的下载和解析 |
| Paper 账户编辑、开户 | 更新账户后额外获取完整 MCP 配置，包含与本次修改无关的配置、密钥列表和审计列表 | 保留账户列表及统计刷新，移除无关的 MCP 总览请求 |
| 看板数据 | 已借用数据库连接的循环内，为每个任务再查订单列表、总数和记忆状态 | 独立的 `dashboard_read_model` 服务用原连接批量读取；订单列表与总数使用同一条 SQL 的一致快照，保留每任务最新 10 条、总数与精确运行身份 |
| 现货定投的看板状态 | 在已借用连接的情况下再次借连接读取调度状态 | 调度检查支持传入已有连接，保留每任务各自的周期判断 |
| 订单与摘要的最新记录 | 缺少按任务、记录 ID 排序的组合索引，历史较多时可能扫描大量其他任务的记录 | 新增迁移 `0012_dashboard_read_indexes.sql`，给订单和摘要各加一个索引，支持现有查询 |
| Paper 分页 | 每条记录分别读取表结构、记录字段和内容长度，产生大量数据库往返 | 每页获取一次表结构与记录元信息，再逐条按内存预算读取内容；继续检查读取中记录大小是否变化 |
| Paper 写入 | `_get()` 已完成兼容初始化，调用方又执行一次 | 删除第二次初始化，减少重复历史证明与投影工作 |
| 数据库副本分析 | 异步接口直接写文件、同步分析上传文件，阻塞同进程的其他请求处理 | 文件写入和分析交给工作线程；保留大小限制、文件清理和原错误响应 |
| 已保存模型配置的发现请求 | 异步请求开始时直接同步读取数据库配置 | 配置解析移到工作线程，原凭据检查和错误响应顺序不变 |

这里的“按需加载”是推迟尚不需要显示的组件代码，不是删掉功能。React 提供 `lazy` 与 `Suspense` 支持这种组件加载方式；异步接口内直接调用同步函数并不会自动放到线程中。[React 官方说明](https://react.dev/reference/react/lazy)、[FastAPI 官方说明](https://fastapi.tiangolo.com/async/)。

## “估值不完整”的实际含义

当前规则要求资产来源及收益依据完整，才显示汇总权益和交易收益。接口已经返回 `completeness.reason_codes`，本次在账户提示及展开详情中把这些原因解释出来，未知原因码也会保留。

| 原因码 | 通俗解释 | 是否属于本次发现的错误 |
| --- | --- | --- |
| `excluded_venue` | 仍有 Binance 范围以外的历史资产或委托 | 现有范围规则，不能直接当成 Binance 资产计价 |
| `unresolved_origin` | 资产或委托来源的证据不够 | 正常保护，不能仅凭名称或字段猜来源 |
| `paper_capital_unverified` | 用来计算收益的本金尚未核实 | 正常保护，不能随意补一个本金 |
| `paper_performance_scan_incomplete` | 相关历史还没扫描完 | 分页中的暂态；不能把部分结果当成全量 |
| `paper_historical_performance_unverified` | 相关历史收益还不能确认为范围内收益 | 当前周期内需要保留；错误地关联到已结束周期时会造成误判 |

本次确认的缺陷是：合法“下海重置”已经建立新资金周期，但收益核验仍把旧周期的非 Binance 或来源不明记录算进去，使新周期也可能持续显示权益和收益未知。修复按已保存的重置事件与账户周期划定核验范围，保留旧事件和原始回执。新周期仍有来源不明交易、扫描未完成或缺失资本依据时，继续显示不完整。

继续检查还确认了三类遗漏：

- 管理员调整账户后的估值读取，没有提交本轮历史扫描进度，导致下一次读取重复扫描；现在保存已完成的核验进度。
- 旧持仓及旧订单的来源核验尚未完成时，部分操作预检拒绝请求会连带回滚扫描进度。现在将来源核验预检与资金修改分开：先保存核验进度，仍拒绝未证实来源的操作，真正的资金修改继续在原事务中执行并重新核验。
- 账户列表按名称排序，但超出末页时使用了按创建顺序确定的结束位置，可能重复返回账户；现在按同一种排序确定结束位置。

这与现有 [账户生命周期规范](../openspec/specs/paper-account-lifecycle/spec.md) 的“重置本轮收益、保留历史审计”一致，不需要重置账户来应用修复。没有证据的资产仍不会用零值、其他交易所价格或猜测价格补全。

## 可以量化的收益

前端数据按生产构建的静态依赖图统计，统计的是页面开始执行前的 JS 文件总量。gzip 是逐文件压缩大小之和，不代表服务器已经开启 gzip，也不包含 CSS、接口响应或稍后才加载的组件。

| 指标 | 改动前 | 改动后 |
| --- | ---: | ---: |
| 首页静态 JS，未压缩 | 1.865 MB | 1.178 MB |
| 首页静态 JS，gzip | 616.6 KB | 394.1 KB |
| 配置页静态 JS，未压缩 | 1.960 MB | 1.339 MB |
| 配置页静态 JS，gzip | 634.7 KB | 442.9 KB |
| 25 个策略任务的看板组装 SQL 次数 | 80 | 7 |
| Paper 返回 N 条记录的一页读取 SQL 次数，普通游标 | `1 + 4N` | `2 + N` |
| Paper 返回 64 条记录的 SQL 次数，普通游标 | 257 | 66 |

Paper 的 SQL 计数不含业务层估值和核验查询；按账户排序且带游标时，两种实现都还需要一次查游标位置的查询。优化后仍逐条读取实际内容并保留容量约束。

看板计数针对 `get_dashboard_data`：测试构造 25 个策略任务和各自的最新摘要，验证返回内容及只借用一次数据库连接；不包括上层其他接口查询或现货定投的额外调度检查。索引验证使用每表 3,000 条记录，确认查询计划实际选用新增索引。[构建大小原始记录](screenshots/performance-20261025/bundle-report.json)。

## 第二轮细节检查与清理

- 统一管理前端读取请求：切换账户、分页或刷新后取消旧请求，旧结果不能覆盖新范围；页码和扫描游标绑定账户范围，切换时从第一页开始。
- 修复修改成功后刷新失败却清空错误提示的问题；刷新时保留正在编辑的 MCP/Paper 设置，保存期间的新编辑也不会被丢弃；已保存的 Paper 设置不会被更早发出的读取结果覆盖。
- 管理操作记录按策略身份隔离，切换策略时取消旧请求，避免显示上一策略的操作记录。
- 删除确认没有引用的 `PositionCycleHistory.jsx`、`paper_storage.max_payload()`、重复订单说明函数和无用导入；保留仍有调用或兼容用途的入口。
- 删除已经没有导入的 `gradio`、`plotly`、外部 `schedule` 依赖。锁文件从 121 个包减少到 94 个包，共移除 27 个直接或间接依赖，保留包的版本不变。表单解析仍使用的 `python-multipart` 保留。
- 修正旧存储测试只安装首个迁移的测试准备，统一使用全部迁移；新增上传分析取消期间的临时文件生命周期回归，确保线程结束前不会删掉正在读取的文件。

## 后续架构建议，尚未实施

本轮采用局部职责拆分：页面负责何时显示组件，看板读取服务负责批量组装展示数据，交易与账本逻辑继续维护资金约束。以下涉及数据更新时间、接口组合或部署方式，需要在下一阶段明确范围后再做：

1. **优先量生产数据。** 对首页、看板与 Paper 看板分别记录首次加载、常规刷新耗时、SQL 次数及数据库连接等待。用相同账户数、历史规模和网络条件对比，避免只根据开发机手感判断。
2. **进一步拆开 Paper 看板与排行榜计算。** 目前一次 Paper 看板请求还会读取账户、订单、事件并计算两类排行榜。可将排行榜投影更新移到独立流程，页面读取最近一次完整结果；必须先明确可接受的更新时间、正在扫描时的展示方式及失败处理，不能自行引入陈旧结果兜底。
3. **按已测慢查询添加索引或调整存储。** 当前大量字段保存在 JSON 文本中，来源证明还要查历史事件。先用真实数据规模与执行计划找出热点，再考虑周期、来源证明、排名字段的专用投影，保留原账本审计。
4. **核对部署中的静态资源传输。** 生产环境可单独检查带版本文件名的 JS/CSS 是否压缩及正确缓存，HTML 是否能及时发现新版本。此项依赖实际反向代理与发布配置，本次未修改服务器。

不建议为提速跳过启动时的数据库版本/配置检查，也不建议未经测量就提高线程或数据库连接数量。当前主要问题是重复工作和加载时机，可以先通过这轮改动减少开销。

## 应用改动时的注意事项

新增索引采用现有版本化迁移流程，未改动已经应用的迁移文件。手动本地启动前需按部署说明执行 `uv run python -m backend.storage.migrate`；镜像启动流程会执行待应用迁移。建索引期间会占用数据库资源并影响相关表写入，大表需要在发布时预留迁移时间。本次未在生产数据库执行。
