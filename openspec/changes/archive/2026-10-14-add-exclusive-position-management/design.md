# Design

## Context

动机与范围见 [proposal.md](proposal.md)。本方案包含三个交付目标：修复当前 MCP 宕机并防止慢调用拖住 Web；让指定管理者持续管理范围内已有及人工变动的合约仓位和订单；将记忆收敛为策略判断、关键价位和有效教训，将收益默认展示收敛为权益变化、盈亏和回撤。

已核实的代码现状：

- `backend/mcp/service.py::market_tool` 每次创建 `MarketTool`，其初始化执行 `load_markets`；行情串行取 ticker/candles，单个交易所请求默认 15 秒，没有覆盖所有阶段的总预算。
- `backend/mcp/tools.py` 使用默认 AnyIO 线程额度；FastAPI 同步路由也使用默认额度。`auth.py` 的异步认证直接访问 SQLite；`store.connection()` 每次运行建表脚本，数据库锁等待上限为 30 秒。
- `guard.assert_position_owner` 以原管理订单及接管基线解释仓位，遇到外部成交即拒绝；`test_position_adoption_gateway.py` 明确测试外部 increase/decrease/net_zero 阻断退出。
- `position_adoption.py` 要求无现存周期及无普通/条件挂单。`independent_cycle_recovery.py` 只恢复原任务完整历史，不接管任意外部仓位。
- `independent_exits.py` 已有自动清理、连续空仓确认、晚到成交处理、版本化回执；新增管理能力复用这些规则，不能删掉周期。
- `execution_ledger.py` 已有成交去重、区间补齐及不完整查询保留检查点；`execution_stream.py` 已有用户成交流，但流不能证明 REST 历史完整，也不能发现所有未成交订单修改。
- 后台 `protection_tick` 主要按已有计划选择维护对象；没有计划的独占范围也必须被发现。Web 与 scheduler 可为两个进程，现有 `threading.RLock` 不能单独防止跨进程竞争。
- 某些未登记订单撤单路径已有 fallback，且对异常尝试另一通道；改造需核查真实阶段，避免把这条路径当成完整外部订单管理，或在超时后盲目二次撤单。
- `execution_ledger.recent_activity_summary` 在自然语言统计后附完整 evidence JSON；`memory_service.format_recent_position_history_for_memory` 将它与权益及完整周期统计一并输入记忆整理。`decision_record.compact_evidence_payload` 精简后仍保留 operation_id/resolution，历史引用还可能由工具调用 ID 回退生成。仅剥离少数引擎字段或要求模型“自行压缩”不足以保证正文干净。
- 用户提供的 ETH 样本同时描述 0.02 多仓、三笔外部挂单、本任务无自有仓位及“账户持仓无”，并复述旧 Edit/批次失败和 unavailable 引用。该样本用于回归矛盾状态和信息噪声，不作为当前真实账户观察；缺周期、成交归属不足及统计窗口不完整必须分别表达。

现场证据与推断必须分开：本次连接器 `list_profiles` 超时，本机公网 `/health` 与 OAuth 元数据在 TLS 阶段失败。尚无生产本机健康、代理或容器日志，不能断言是交易所、线程池、数据库锁或 Nginx 中某一项造成当前宕机。

## Goals / Non-Goals

**Goals:**

- 独占授权一次配置，启动和运行期间持续生效；模型继续使用现有规范工具。
- 仓位、普通/条件订单、成交和周期边界使用共同事实与版本；外部变化可追溯。
- 前台只核验本次必要事实，后台持续补齐；本地纳管与交易所写入分离。
- MCP 公网链路恢复有独立验收，慢依赖不会持续耗尽 Web 能力。
- 记忆正文与当前事实、收益摘要、后台诊断分开生成，周期和恢复流程不再由 Agent 维护。

**Non-Goals:**

- 第一版不做现货底仓自动接管、附带保护模式改造、不同策略共享净仓的数量分配或新增交易策略。
- 不默认启用所有账户，不自动等比例修改固定档位，不自动把人工重开解释为补平指令。
- 不把外部交易伪造为 Agent 工具结果，不让 read 工具发起交易所写入。
- 此次 propose 只生成规划。生产修复涉及的实际配置调整、发布和重启在 apply 中依证据和授权执行；无法访问生产时该项保持未完成。

## Decisions

### 1. 配置授权与交易决策分开

任务及 MCP profile 增加 `position_management_policy=strict_owned|exclusive_scope`，默认 `strict_owned`；独占模式指定有限的规范交易对及 LONG/SHORT 范围。MCP 的 `symbol_scope=all` 只代表可访问市场，不能自动获得全部市场的独占管理权。第一版仅为明确列出的范围配置独占管理。

管理者使用内部 `config_id` 或 `mcp:<profile_id>`。多个 MCP principal 可在原 profile 授权内操作同一管理者，但不能因同账户建立另一个 owner。临时聊天不自行申请 owner，绑定任务聊天沿用任务 owner 和审批。启用前核查现有任务计划和执行记录的竞争归属；已有同 owner 周期可无缝继续，其他有效 owner 不能被抢占。

替代方案：删除周期检查会丢失旧条件单和提交身份；逐轮手工 adopt 不能应对持续人工干预。两者均不采用。

### 2. 以数据库持久化范围和跨进程操作保留点

增加独占范围记录，包含 account_scope、canonical_symbol、scope_side、owner_config_id、policy_revision、state 和观察信息。Hedge 可 LONG/SHORT 分别唯一；One-way 必须共享 BOTH 范围。配置、删除、导入导出和凭证变更通过同一事务校验互斥及活跃资源。

复用 `trade_scope_generations` 和周期版本 CAS。外部发现与纳管通过短 SQLite 事务提交；网络查询在事务之外。为系统金融动作增加持久化 scope reservation，记录 operation_id、client_id、动作阶段及 owner，跨进程不得同时提交冲突动作。reservation 不能仅因租期到期就证明未执行：崩溃后先核验原身份，再释放或推进。

现有 account_scope 使用交易所 ID 与 API Key 哈希。第一版要求同一物理交易所账户使用统一的保存账户/凭证引用，合并相同凭证的 profile 别名；不同 API Key 实际属于同一物理账户的场景不得声称已自动识别，启用前需统一账户引用。多 Key 自动账户身份识别不纳入此次实现。

### 3. 统一发现与纳管服务，保留原始事实

增加 `backend/utils/position_management.py`（建议模块名），组织 scope resolution、discovery、enrollment 和 reconciliation，供 scheduler、执行层及查询投影复用。

事实包括：仓位基线、后续成交、普通订单、条件母单/子单关联、订单原生参数、管理来源、真实观察时间、完整性及所属周期。来源采用 `agent`、`external`、`baseline`，无法证实操作者时不标为“人类”。外部订单缺少 Agent reason 时保留为空及来源说明，不编造模型交易理由。

普通和条件身份沿用 `regular:<id>` / `algo:<id>`；成交以 account/symbol/trade_id 去重。先按 client_id 匹配未知 Agent 提交，再考虑外部纳管。存在其他有效 owner 时返回真实竞争，不将其作为 external。不同渠道分页和 OKX 各 algo book 分别标完整性。

已平仓且从挂单列表消失的外部订单仍可从成交识别，补查订单终态并登记历史关联。对无仓位但有入场挂单的范围建立 WAITING 管理记录；不伪造持仓，也不让 close 提前安装未来退出单。

### 4. 接管基线与完整成交检查点组成数量依据

先尝试恢复原 owner 周期。确实无可恢复历史时，在独占授权下读取稳定仓位、挂单、交易所时间及重叠成交边界，二次核验并创建接管基线。基线是 observed inventory，不创建假入场订单或假 fill。

基线时间之后：当前可解释仓位 = 基线数量 + 已核验入场成交 - 已核验退出成交。历史边界重叠分页按成交 ID 去重，部分失败不推进检查点，避免把启动前成交重复计入基线。来源外部的成交也参与解释；先加后减、最终量相同仍记录两笔事实。

复用 ledger 的有界区间补齐替代 guard 的单页 1000 条所有权判定。同步不上或差额无法解释时记录证据缺口，不直接把当前快照差值当作一笔真实交易。历史 PnL 和手续费缺失继续 unknown；基线纳管不能补造历史收益。

### 5. 未成交外部订单必须主动轮询

已配置范围即使没有现存周期，也进入后台发现集合。默认后台合并同范围请求，正常发现周期 30 秒，失败指数退避至 60 秒；这些值可配置，用户成交流提供变化提示，REST 负责补齐。

读取普通订单及适配器支持的完整条件订单集合，核验持仓模式、方向、reduce-only/closePosition、原生类型与实际成交，建立入口/退出作用及能力信息。部分成交后仍管理剩余量。已纳管且人工修改的订单通过原身份更新，模型省略字段时使用最新值，不还原旧参数。

范围外、未知方向和不支持的类型仍可展示，但只有可证明依赖满足的动作可执行。固定与 dynamic all 按实际原生语义映射；不能把没有固定数量的原生全平单推断成零数量。

纳管过程不取消任何单。后台清理仅针对已经记录到将结束周期、且其清理意图已授权的订单，不按“当前账户所有挂单”批量撤销。

### 6. 外部全平、晚到成交和重开保留明确周期边界

继续使用 WAITING/ACTIVE/EXITING/DONE，额外记录管理同步状态 verified/partial/conflict；sync 失败不是所有动作的全局开关。

```text
configured scope --> discover --> restore or enroll --> WAITING / ACTIVE
                                                     |
                        verified zero / closure fills v
                                                   EXITING
                       cleanup verified + flat ------> DONE
                       late fill / residual ----------> ACTIVE

DONE + verified external reopen --> new ACTIVE cycle
```

外部全平有独立事件，Agent 后续 close 在可靠空仓时 skipped。不能把人工成交回写成原 Agent close 的成功。外部全平后重开需以完整成交序列识别旧仓已归零和新仓建立；旧 all 单安全性不明时禁止受其影响的新风险增加，但允许依赖已核验残仓的管理。

旧周期清理只针对旧周期登记单。新发现于已核验归零边界之后的入场单登记到 successor/WAITING，不盲目归入旧周期清理。来源和成交边界不明确时保留具体订单 pending，不能猜测并撤单。没有自动重入策略；这里只接续已经发生的外部新入场。

### 7. 交易前自动核验、纳管与重新准入

执行入口在原 operation_id 下解析 owner、取得范围协调，做动作依赖的有界取证；需要时本地纳管或恢复，再进入现有 independent_admission。移除 exclusive 模式下“非 Agent 创建即拒绝”的 blanket gate；strict 模式继续原规则。后台维护与查询共享证据分类。

固定 amount 不静默缩成当前剩余量。close_all 在提交前重新读取实际剩余量；条件 all 保持交易所原生能力约束。退出必须使用适配器真实的 close-only/正确方向语义，不能因人工并发减仓反向开仓。

人工操作不受应用锁控制，提交前核验只能减少竞态，不能保证交易所状态不再变化。结果按真实交易所 ACK 和后续成交判断，拒绝/部分成交/未知保留，不通过重发取得可用性。取证内部不撤改无关单，不自动恢复旧参数。

外部单的 edit/cancel 统一走已纳管目标路径；审查旧 unmanaged cancel 的异常 fallback，网络超时不能触发盲目更换通道重试。原操作哈希和回执版本保持兼容，新增 management/evidence 元数据不加入旧请求默认字段。

### 8. MCP 宕机先定位，再按证据修复

实施第一阶段采集同一时段的证据：服务器本机映射端口与容器内 `/health`、容器状态/资源/日志、入口监听和 DNS/TLS、Nginx/宝塔 access/error、公开发现路径及已授权 MCP 请求。只采集必要脱敏数据，不读取或记录完整 `.env`。

按现场结果修复入口网络/TLS/证书/反向代理、容器异常或应用阻塞；不预设修改代理超时是修复。代理改变需核验配置语法、保存原配置及回退方法；容器重建需保持数据卷和密钥，不能丢弃未知交易记录。生产变更按 apply 阶段实际授权执行，无法完成生产访问时该工作包保持待完成。

公网验收包括首页、`/health`、OAuth 两类元数据及 issuer/resource、认证 `list_profiles`、分别测试账户/订单/行情。用只读调用验证；每个结果保留时间和失败层。不能把部署镜像成功或本地健康成功当作公网修复。

### 9. MCP 总预算与服务额度独立

为 read 和金融 execute 分别提供专用 AnyIO limiter/有限排队，避免使用 Web 默认 limiter。建议初始值：read 并发 4、execute 2、认证/存储 2；read 排队 2 秒、总预算 20 秒，单依赖读取最多 min(8 秒, 剩余预算)。部署变量可下调，最终值以离线故障注入和目标机资源验证为准，不无限提高线程数。

总预算包括排队、初始化、市场加载、交易所读取及返回持久化，阶段之间检查剩余预算；同步 requests 无法仅靠外层 asyncio timeout 强行停止。单个底层网络 timeout 必须受剩余预算约束，预算耗尽不再启动后续查询，尚在运行的 worker 保持占用直至真实结束。断开请求不通过 abandon_thread 提前释放实际并发额度。

金融写入在提交前持久化原操作与身份。请求超时/断开后仍运行的阶段继续被追踪，不能套用只读取消逻辑释放 scope reservation，更不能生成新 ID 重发。总预算过期前未提交则返回明确未提交；已可能发送则保留 unknown/pending 和原查询入口。

`store` 建表移至 `init_db` 的启动迁移，读操作不运行建表脚本；认证将同步数据库操作卸载到受限线程并设置短、可配置数据库等待预算。敏感访问及 audit 失败不覆盖已有金融执行事实。

### 10. 市场缓存与返回兼容

按交易所/market_type/账户配置版本复用不可变市场目录，建议 TTL 5 分钟、同 key 单次刷新、有限失败退避；实例通过复制元数据装载，不在并发请求间共享可变 CCXT 客户端。跨实例账户调用通过账号级限速协调，避免每次创建实例绕开真实请求权重控制。凭证变更使相关客户端及缓存失效。

公共 ticker 可短缓存（建议 2 秒），candles 可按 timeframe/limit 缓存（建议 15 秒），都保留实际 observed_at。私有仓位/订单历史缓存可供展示，不能直接证明写入准入。余额不等同可管理仓位。

`get_orders/get_positions/list_profiles` 成功保留列表形状；订单通道不完整时返回明确工具错误及缺项，不用部分列表冒充完整结果。`get_market` 保留原字段并增加 status/missing_sources/observed_at 表达部分成功。采用原 MCP 错误机制传递繁忙/超时及阶段，保留调用者可识别的说明，不新增模型必填参数。

请求日志包含 request_id、阶段耗时、脱敏范围、结果、并发与队列指标；不记录凭证、完整 OAuth 查询串或交易所认证头。

### 11. 用当前事实驱动界面与模型

复用 `project_trade_state` 及 Agent/Chat 现有投影入口，补充管理范围、owner、来源、当前外部变化摘要、订单管理能力和完整性。同步成功的 external 不标成永久 blocker；策略继续决定保护是否调整。

任务和 MCP 管理页增加“独占管理范围”的配置及简短说明，显示是否已完成核验。仓位/订单界面显示来源、支持的动作、观察时间、对账缺项、数量冲突与保护估计。所有页面同步中英文；实现保留本地现有 provider-model-discovery 修改。

### 12. 记忆只承载策略，执行恢复留在后台

新增正文格式使用“策略判断 / 关键价位 / 有效教训”三个栏目，空栏目可以省略。四小时收盘、CPI 后观察等有策略意义的等待条件保留；持仓数量、挂单列表、收益数字、旧工具失败、操作 ID、resolution、周期状态和“先查历史 ID 才能交易”的恢复步骤不写入正文。有效教训需来自具体策略或已核验经验，不每次追加相同的泛化警告。

记忆素材在程序侧做语义投影，不把完整 performance_context、recent_activity_summary JSON 或 compact_receipt_payload 直接交给模型作为待复述正文。后台仍保存原工具回执、成交账本、执行引用与来源校验；source ID/hash 属于发布校验元数据，不能复制进正文。operation 引用由程序关联与更新，记忆模型负责策略整理，不负责判断某历史 ID 是否已解锁。

`summary` 与默认已发布 `memory.strategy_text` 均遵守纯策略正文约束；完整的原始工具与账本保留在独立已有审计数据中，而非靠新记忆 summary 再保存一遍。沿用现有投影输出契约和来源校验，内部执行关联由后端补齐；不得为简化文本丢失原真实未知提交的身份。

更新 `memory_service`、`context_projections` 和 `decision_record` 的素材与输出规则，校验新正文不含 operation_id/resolution、周期诊断、收益统计或账本 JSON；不按固定字符数硬截断。格式错误按现有有界修正和后台重试处理，保留有效策略判断和关键价位。

对已存在的嘈杂记忆升级投影版本并后台转换，保留旧原文供历史审计，不批量删改历史记录。默认详情接口/记忆卡展示纯策略视图；旧审计原文通过明确的历史详情入口读取，不在转换失败时回退到默认 Prompt 或普通记忆正文。主规范要求保留完整源正文是保留原证据，不是要求复制到新记忆。

### 13. 当前状态不由历史周期或失败文本推导

当前持仓来自交易所观察；“没有自有周期”“暂无已归属成交”“账本无开放周期”不能覆盖这个观察。管理范围、当前仓位与本任务归属分别维护，但默认给 Agent 的表述围绕实际仓位、可管理挂单和本次需要处理的事实，不重复内部计数和长篇恢复说明。

后端对历史引用分别判断：确认未提交、明确拒绝、未执行、真实结果未知、已解决或仅查询不可用。历史 tool_call_id 不自动等同可查询 operation_id；operation_id=null 不生成虚构恢复目标。旧 Edit 归属拒绝及 stop_on_error 未执行尾项保留审计，不因为 resolution=unavailable 再包装成当前阻塞。

有真实未知提交且会改变本次剩余量时，后台继续核验，当前状态可简述“某退出结果仍待确认，影响本次数量核验”，详细 ID/阶段按需查询；不能因为正文省略 ID 就解除依赖。无关历史读取失败不进入当前待处理事项，也不要求模型 Get_trade_operation 解锁。已有工具和批次结果仍保留准确身份供显式查询。

### 14. 收益三类指标与按需详情

从既有统计数据直接生成确定性的简明摘要，不先渲染长篇 ledger JSON 再交给 LLM 压缩。REAL 与 STRATEGY 使用各自数据源，默认只有：

| 指标 | 默认内容 | 必须保持的含义 |
| --- | --- | --- |
| 权益变化 | 当前可用快照权益、起点至该快照的金额/比例变化 | 历史快照，非实时余额，也不是 Agent 独立交易盈亏 |
| 盈亏 | 可可靠归属且口径完整的已实现/未实现金额；缺失显示暂不可统计 | 标明时间区间及费用处理，已实现与未实现不混用、周期盈亏不重复相加 |
| 回撤 | 当前回撤及最大快照回撤 | 明确来自权益快照，不承诺覆盖所有盘中极值 |

各指标保留短区间/截至时间和必要口径标签，复杂定义放详情。保留现有计算公式；未剔除资金进出或共享账户影响的权益变化不改名为 Agent 独立收益。已实现收益采用可归属成交金额，不依赖完整周期数；真实完整的零值可以显示，缺失/归属不足不能以已知子集的 0 伪装全窗口盈亏。

详细账本由按需详情入口提供成交、费用、归属缺项、完整周期、同步覆盖与原操作回执，按现有权限控制。默认收益区不显示胜率、完整周期笔数、窗口 boolean、同步区间、active_protection/execution_review 或整份 JSON；零周期不能被描述成零交易。详情可分组展示，原始 JSON 留在明确审计展开层，不自动注入下一轮记忆或普通交易 Prompt。

用户样本的预期展示如下（仅说明历史样本格式，不是当前账户状态）：

```text
权益变化：589.00 USDT，较起点 -2.12 USDT（-0.36%）。
盈亏：近7天数据归属尚不完整，暂不可完整统计。
回撤：当前 0.36%，最大快照回撤 0.36%。
权益快照截至 2026-10-14 12:00；起点 2026-10-14 00:00。
```

该样本不再默认展示 0 笔完整周期、0 条已归属成交、5 条未知归属、7 条未匹配以及重复 JSON。它们仍在详情中；真实已核验金额可以在不虚报窗口完整性的情况下按明示口径展示。

## Risks / Trade-offs

- [交易所无法原子锁住人工操作] → 提交前再核验，执行真实 close-only 语义，保存阶段并追踪部分/未知结果；不承诺并发变化零延迟。
- [两个进程或崩溃后重复写入] → 持久化 reservation + CAS + 操作幂等；租期到期不自动证明未执行。
- [不同 API Key 指向同一物理账户] → 第一版要求统一账户引用，明确不能仅凭 key 哈希声称完成物理账户互斥。
- [首次接管没有全部历史] → 记录观察基线和边界，不补造历史收益；历史与本次管理事实分开。
- [旧 all 在人工重开后仍有效] → 保留旧订单关联和目标级限制，核验并清理旧周期，不把旧 all 算为新仓保护。
- [未知外部订单语义或适配器能力] → 不猜测类型/方向，只对其相关动作返回能力限制；读与其他可核验动作继续。
- [总预算到期但同步 worker 未结束] → 底层 deadline 与实际占用计数一致，有界并发/排队，故障注入验证不会线程泄漏。
- [现场故障属于公网层] → 单独执行证据驱动修复及公网验收；生产访问缺失不隐藏为已完成。
- [精简可能误删真实未决风险] → 当前事项按本次动作的证据依赖筛选，后台身份与原回执完整保留，记忆简化不修改执行准入或重发未知写入。
- [旧记忆或失败回退重新带入内部字段] → 升级纯策略投影版本，校验新正文，默认路径不回退到旧噪声；原文只按需审计。
- [零周期或不完整归属导致盈亏误报 0] → 摘要基于可靠金额与完整性，缺失显示暂不可统计，权益变化和归属盈亏分别标口径。

## Migration Plan

1. 优先采集当前 MCP 宕机证据并完成最小故障修复；保存现场变更和回退依据。应用加固在独立工作包验证，不必等待仓位功能完成才处理入口故障。
2. 增量创建范围、reservation、外部事实/基线及观察检查点结构，默认 strict；保留历史 DB、请求和回执，不重新归属旧成交。
3. Web 与 scheduler 统一更新到支持该结构的版本后，为指定 owner 显式配置有限独占范围，运行只读发现及本地纳管验证，再启用后续策略管理。
4. 完成离线场景、权限、幂等和并发可用性回归及前端构建；生产只读 smoke 不提交、修改或撤销订单。
   同时发布纯策略记忆视图和简明收益展示，后台转换旧投影；保留原记忆、账本与历史回执。以 ETH 用户样本回归三类摘要和默认输入，确保旧错误不再形成解锁清单。
5. 若请求归档发布，遵循现有 archive-release-workflow 和 release 脚本；镜像发布不隐含生产重启。生产 rollout 及本次故障现场变更按实际授权分别记录。
6. 回退优先暂停新风险增加、保持支持新管理事实的维护版本并完成活跃生命周期，再关闭独占策略或回滚程序；不能在交易所状态变化后恢复旧数据库掩盖成交。代理/TLS 的回退与应用/DB 的回退分开。

## Acceptance Matrix

| 场景 | 验收结果 |
| --- | --- |
| 启动前已有仓位及普通/条件挂单 | 自动纳管并允许原管理调用，不要求清仓或手工 adopt |
| 人工加仓、减仓、先加后减 | 成交连续去重，管理量更新，依赖满足的工具继续 |
| 人工提前全平 | 外部平仓可追溯，清理核验后 DONE，无重复 close |
| 人工新增/改单/撤单 | 原身份与参数同步，可 edit/cancel；不自动恢复旧参数 |
| 外部单部分成交/条件母子切换 | 持续管理实际剩余量和当前身份 |
| 人工全平再开及清理晚到成交 | 周期边界正确、旧单不误保护新仓、残仓可管理 |
| 两个 owner / Web 与 scheduler 竞争 | 范围互斥、只纳管一次、冲突写入协调 |
| read-only、cancel scope 缺失、聊天拒绝审批 | 原权限约束保持，查询不发起金融写入 |
| 断流、分页缺口、未知提交 | 保留原身份和事实，不重发、不假报空仓或完整列表 |
| MCP 交易所慢调用与 DB 锁竞争 | 并发与预算有界，Web/异步入口维持响应 |
| 当前公网宕机修复 | 现场故障证据、调整记录、公网 TLS/OAuth/MCP/Web 验收完整 |
| 含 operation_id/resolution/周期报错的旧记忆 | 新正文只有策略判断、关键价位和有效教训，旧证据按需审计 |
| ETH 0.02 多仓及三笔外部挂单、无自有周期 | 当前状态如实显示交易所仓位，后台纳管后工具可管理，不写无持仓 |
| 旧 Edit 拒绝、null ID、批次未执行项及 unavailable 引用 | 不形成当前解锁清单或无关交易禁令，真实未知提交仍由后台按依赖核验 |
| 权益快照可用但7天成交归属不完整 | 默认仅三类指标，盈亏暂不可完整统计，不默认显示零周期、胜率或完整 JSON |
| 已实现盈亏可靠但周期尚未闭合 | 可靠金额按对应口径可见，不等待完整周期数才显示 |
| 用户主动查看账本详情 | 可查原始成交、费用、周期及同步证据，历史时间明确，内容不自动进入记忆 |
