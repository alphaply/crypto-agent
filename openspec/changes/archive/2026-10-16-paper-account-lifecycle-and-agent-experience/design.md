# Design

## Context

动机与范围见 proposal.md，验收契约见十一份增量规范。只生成规划，不调整主规范或业务代码。

已核实的现状：

- 新闻 HEAD 使用距 last_attempt_at 的滚动间隔；工作区 `news_service.py`、`news_schedule.py`、`NewsSettingsPanel.jsx` 和 `test_news_schedule.py` 已有未提交的定点修复。截图来自 `NewsPipelineMonitor.jsx` 的 started_at。
- `DecisionMessages.jsx` 的 ToolReceipt 先显示核验信息，再交给 ToolResultContent 重复递归展示；后者默认展开多层结构。聊天普通工具外层已有折叠。
- MCP v3 使用 `compact_trade_receipt` 投影结构化事实，内置路径另有 `render_trade_receipt`；在途 `simplify-memory-and-ordered-execution` 已拥有默认模型简短文本契约。此计划不以更改模型载荷解决前端重复展示。
- `paper.py` 的 bank 固定零利息，PaperSettings 缺少日利率；`number` 拒绝负数，被现金快照及交易计算广泛使用。只允许写负现金而不修读取路径，会令后台和榜单出错。
- `_write` 使用账户锁和原操作幂等回执；Paper 批次、订单和事件由 PostgreSQL 持久化。`paper_schema.py` 不创建表，迁移通过 `backend/storage/migrations/` 显式执行。
- `paper_orders.match` 对普通停用账户主要拦截入场，不能承担本次“破产订单不成交”的契约。`reconcile_instrument` 还会更新仓位和爆仓，必须统一受破产状态门控。
- 现有榜单按 performance_pnl / competition_capital 计算 return_pct，支持 pnl 排名；资本调整、估值完整性、隐私和分页能力需保留。
- 可信 QQ 发件人绑定由外部机器人集成和 skill 提供，Paper key 目前主要隔离 namespace。仓库有 bot 账户及人格/skill 分发资料，但无外部实际自主定时任务配置；人格没有明确区分自有账户自主授权。
- 精确报错来自 visible_management.claim_management：物理账户、市场、实际资源及重叠方向已有其他 owner 时拒绝。live 的 management_action 覆盖开平仓、撤改单和保护；旧 exclusive_scope 另有排他逻辑。Paper 与 STRATEGY 不走此报错路径。visible-position-management、exclusive-position-management、撤单/现货规范及状态投影当前均存在长期独占约束，本次增量必须一起取代。

## Goals / Non-Goals

**Goals:** 用共享账本事务、账户周期和明确的权限分支实现已确认行为；使定时轮询和前端展示可以独立验证；所有资金效果可重放核对且不可重复产生。

**Non-Goals:** 不新增交易所、报价替代源、独立机器人调度器、强制交易频次或实际灰色工作系统；“下海”仅是用户主动请求重置的角色表达。不重写其他在途变更的记忆与模型回执方案，不在本次提案中执行部署或外部账户交易。

## Decisions

### 1. 接续已有新闻槽位修复

复用当前本地 `news_schedule_slot` 及新闻状态存储，把间隔锚定北京时间零点，确认每个槽位只有一次逻辑触发。保留当前租约防重入、错过槽位不积压补跑、手动更新和公告触发行为，不新增超时策略。对 12:30、13:00 和错误后下一槽位验证即可。Agent 自身 run_schedule 已对齐，不因截图误改另一套调度器。

### 2. 将显示摘要与执行事实分离

前端建立可复用的摘要投影，优先识别 results/result、原始文本和通用查询内容；只选状态、目标、必要交易事实与简短原因。DecisionMessages、运行进度和 ChatPage 共用卡片，移除现有首段与完整树的重复呈现。完整原结果、原始 JSON 和 AuditDisclosure 放在用户主动展开的区域。纯文本模型返回和结构化 MCP 结果均可消费，不更改后端事实、大小契约或模型提示以美化 UI。

### 3. 将破产状态与管理员 enabled 分开

账户增加独立生命周期状态与 account_epoch；普通 enabled 保持原有管理含义。净权益判定只使用完整估值；计息扣款不足直接标记破产。读取状态不是金融操作。破产状态拒绝用户金融写入，允许可信下海重置、收款及每日计息；收款不清除该状态。

账户锁内执行统一准入：批次每项、兼容写入口、匹配器、条件保护和后台金融维护都复核生命周期与周期。冻结已有订单而不自动取消；不执行冻结订单的入场或退出，也不通过后台爆仓路径绕过冻结产生交易变化。只读估值可以更新，原历史事实可以核对。

### 4. 资金类型与双账户转账

保留输入 amount 的正有限 Decimal 校验及最多八位小数；单独提供有符号现金解析供已存账本、快照和计息使用，不放宽借款、还款、转账或下单金额校验。禁止浮点 NaN/Infinity 和布尔值参与资金计算。

新增 `paper_transfer(user_id, recipient_user_id, amount, operation_id)`。付款身份遵循现有可信集成授权，不接受昵称自称或正文冒充；收款按稳定 ID 解析。事务按稳定顺序锁住两个账户，先检查原操作指纹和幂等结果，再重新核验付款账户正常、可用现金及双方周期；一次提交双方现金、资本调整、成对事件和回执。禁止借助负金额、旧周期或并发预留透支。相同身份跨请求重试返回同一逻辑结果，改变金额或收款人拒绝。单账户 `_write` 不被顺次调用两次来模拟转账，避免半边成功和死锁。

### 5. 统一银行及可重放计息

在统一 Paper 设置中增加借款开关及日利率，额度使用后台统一规则；现有单账户额度显示/接口应与统一政策保持一致，不能暗中继续覆盖统一配置。`management.py`、设置导入导出、上下文、默认/兼容银行工具和前端使用同一配置来源。

持久化带生效时刻的利率修订、借还本金事件、计息结算游标与期间明细。按北京时间日界分割、按实际秒数计算本金 × 当时日利率 × 时长/86400，先以 Decimal 累积再按账本精度结算。本金变化与调息都形成区间边界；利息从 cash 扣除，不增加计息本金；负 cash 不产生复利。重复运行由唯一期间身份及账户锁保证只扣一次。

接入现有后台维护生命周期，但计息账户扫描必须包含无持仓、无挂单及已破产的借款账户，不能只从 instruments 推导。与撮合、转账、重置共享提交锁，计息不足时同一事务设置破产。重置后旧期间不得扣新周期现金。旧账本在启用新配置前维持原有零利息事实，不补造历史利息或未知借款时长。

### 6. 显式重置与不可变历史

复用 configure_paper_account 的 `action=reset`，保留 create/update 原意图。人格和 skill 只在本人明确主动说下海时提交 reset；接口检查用户账户、破产状态和幂等身份。不要加入 bot 主动劝下海、后台审批、次数上限或第二次机械确认。

单一事务终止旧周期未成交资源并释放旧预留，清空当前仓位/库存/债务/负现金/本轮损益及账户参数，调用与开户共享的初始化逻辑恢复后台当前初始状态；保留稳定用户身份、全部不可变历史和累计下海次数。建立新 account_epoch 并更新计息起点。操作身份不因新周期可再次使用；旧响应返回历史事实，但旧批次、旧匹配任务和旧利息游标不能写入新周期。下海次数和周期切换与现金补款原子提交。

### 7. 双榜与资本调整

公开查询改为 `metric=return_pct|reset_count`，pnl 不再是排名指标，旧请求明确提示支持的指标，禁止静默改义。交易榜继承现有完整估值及资本调整公式：净权益减经资金流调整的本轮 competition_capital 得本轮损益，再除以正的计分资本。转账对双方作相反资本调整，借款增加等额现金与本金债务、因此不产生利润；利息减少净权益并计入损益。无有效分母或估值不完整时沿用不参与收益率排名的现有行为，不编造零收益。

reset 建立新的本轮资本和收益起点，例子 10000U 重置后赚 2000U 为 +20%。下海榜读取持久化累计次数，不依赖旧轮损益；沿用排行榜隐私和公开参赛偏好，不为新榜泄露私人资金。后台同时可查看状态、周期和下海次数，公开榜与后台使用同一数据口径。

### 8. QQBot 人格、skill 和工具说明协调

先区分 `bot_user_id` 自有账户与可信用户委托：前者已获自主决定交易参数授权，后者仍缺什么问什么。更新人格及 skill，使现有定时唤起流程读取自有账户、行情/新闻，形成具体执行或观望判断；有决策时实际调用 execute_trade_actions。提供可复用的自主定时任务提示片段，并更新分发包，供既有外部任务接入，不声称已修改无法访问的外部部署。

正常回复按真实回执说委托或成交，不主动输出模拟标签；工具说明去掉反复要求模拟免责声明的文字，但保留内部 execution_mode、授权隔离和如实回答资金性质的规则。主动接济只从 bot 账户转账，破产用户可以收款；任何用户未主动说下海都不调用 reset。不懂黑话主动询问，不将角色设定当作用户账户金融授权。

### 9. 全局移除长期独占，保留共享资源执行协调

这是已确认的全局规则，不新增按连接白名单、抢占、释放 owner、人工交接或继续独占的配置开关。当前 visible_first_claim 与旧 exclusive_scope 在新请求中统一使用可信范围内的共享管理；旧 owner 仅作为来源审计，不再影响其他已授权调用者的金融准入。管理查询、工具说明和错误投影也不能将另一 owner 换名为“只读”“不可修改”继续阻断。

拆分现有 management_action 中的长期归属检查和执行协调。共享资源键继续由可信物理账户、市场与实际资源导出：合约 Hedge 分方向、One-way 共用 BOTH，现货按基础币跨报价币共享。跨进程文件锁/数据库锁及版本校验必须按物理资源协调，不能按 profile 或 owner 各锁各的。锁只保护实际准入/提交阶段，不建立长期排他管理者。保留权限、启停、标的、市场、精度、固定量/全平和审批检查，操作 actor、profile、principal 与原幂等指纹也不改变；不同用户账户和 Paper namespace/user 不因此合并。

以资源的当前有效订单/保护意图修订协调共管。已有订单、周期、预留和核验事实按真实身份共享关联，不为每个连接复制一份仓位或库存基线；原来源字段仍可审计。A 设置保护后 B 成功明确修改或撤销，对同一目标发布新的有效修订。后台 worker 提交前重核当前修订；旧修订的维护只观察/恢复原事实，不重新挂回被取代参数。只有成功提交的明确修改推进有效修订，失败不覆盖成功值，pending/unknown 仍由原身份核验；不以模型请求时间、轮询先后或迟到 ACK 覆盖较新的已成功意图。多个独立目标和未被明确修改的其他保护腿沿用原动作语义，不引入额外隐式撤单。

改平撤及保护可以作用于另一连接创建的资源，但需原有目标身份、当前数量、能力及动作权限。共管不向另一 principal 自动公开旧私有操作回执；后台按原身份继续核验未决写入，恢复所需的显式资源级授权仍保持最小范围。另一连接的新明确请求使用自己的新操作身份，不能复制旧未知提交重发来取得可用性，也不能自动续跑旧批次尾项。

迁移时保留已有 claims、资源 links、基线、订单、保护意图和回执作为事实及来源，使其 owner 字段不再产生排他准入。已有维护转入按共享物理资源和有效修订去重的执行通路，避免每个连接都运行同一保护写入。不通过直接删 claims、释放预留或强行终结未知状态解决报错；升级后历史独占状态不能在重启或后台发现时重新生效。旧配置可以读取，但不能恢复唯一 owner 行为。

## Risks / Trade-offs

- [有符号现金冲击现有非负解析] → 逐一检查 snapshot、银行、预留、计分和前端格式化路径；只对账本现金放宽，不对金额输入放宽。
- [读到破产前状态后并发成交] → 行情在事务外读取，提交锁内重读状态和周期，覆盖新旧入口及维护线程。
- [收款、调息或 reset 与旧游标并发] → 稳定锁顺序、唯一结算身份、周期检查和原子资金/事件/回执提交。
- [提示词不等于外部实际自主任务已修复] → 仓库内做工具能力与指令一致性验收；最终外部任务验收需观察部署端实际唤起、下单或具体观望证据，不承诺每轮必成交。
- [与已有本地修改及在途回执计划冲突] → 实施前按文件检查差异，只接续相关修改，不清理无关文件或覆盖另一变更。
- [破产冻结仍保留资产与挂单] → UI 明确状态，收款不自动恢复，旧订单只能在主动下海时终止，避免无提示恢复成交。
- [仅删除报错使旧保护线程争相恢复参数] → 共同更新归属准入、物理资源锁及目标修订，跨进程验证后续成功修改不会被旧 worker 覆盖。
- [历史归属被当作账户权限或私有回执授权] → 将来源与准入拆开；共管仍逐项校验当前可信权限和原回执访问范围。

## Migration Plan

1. 为新增周期、转账、利率与结算事实编写显式 PostgreSQL 增量迁移；旧账户初始累计次数按无历史重置的事实初始化为零，不重置已有资金、债务和仓位，不伪造历史收益。
2. 更新账户升级和有符号现金读取，部署前先在隔离数据库验证旧账本、幂等回执和新表约束。复用现有备份/迁移流程，不在应用启动时临时建表。
3. 先完成共享生命周期、转账/计息/reset 和榜单，再更新 MCP schema、后台界面与人格/skill 分发；分别验证只读、可写、live 与 bot 身份。
4. 新闻与回执界面可独立验证；模型简短文本所属变更如先落地，此处按新文本消费，不合并其未完成任务。
5. 真实账户共管先建立统一资源协调及维护修订，再停用长期 owner 拒绝；升级现有 visible_first_claim/exclusive_scope 配置并保留原未知提交身份。验证旧连接、其他连接与内置 Agent 的跨进程协作，不通过实盘交易验证。回滚不能简单恢复旧后台意图或删除新修订，必须保留最新成功修改与所有执行事实。
6. 本次 proposal 不执行迁移或发布。将来部署按仓库流程另行操作；出现账本问题先停止金融写入并保留审计，不将存在负现金/新周期数据的数据库直接交给旧版非负解析代码。必要回滚使用验证过的代码/数据库配套备份，不丢弃新金融事实。
