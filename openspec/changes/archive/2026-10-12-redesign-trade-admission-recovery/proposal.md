# Proposal

## Why

当前下单路径把历史失败、整个周期的对账异常和本次交易依赖混在一起：已明确拒绝且没有订单 ID 的止损会持续阻塞新止损，查询回执却可能显示没有限制。用户已确认全面重设计 open / close / edit / cancel、恢复及批量执行，使系统只阻止存在具体执行冲突的动作，减少正常交易被连带中断。

## What Changes

- 将 Agent 调用顺畅作为首要验收目标：有效动作可直接调用，系统内部完成必要的有界取证和状态刷新，不要求先查询、手工解锁或等待下一轮。每个额外阻塞必须有具体硬约束或相关执行证据，不以猜测业务顺序新增限制。
- 以结构化执行证据和动作依赖替代 `plan.error`、无订单 ID、前项 failed 等全局开关；区分明确未提交、结果未知、正常在途、成交待核验和历史告警。
- 将交易前的只读取证与周期清理、撤建维护分离。新动作核验自身所需事实，无关维护失败不成为前置条件；缺失周期仍通过原归属证据恢复。
- 按增加敞口、减仓/保护、目标改单、目标撤单分别判断，保留权限、归属、幂等、数量/方向和交易所能力约束；真正的未知提交继续限制依赖它的动作。
- 让交易回执、原操作查询、Agent 上下文、MCP 与 UI 共享准入解释，展示具体阻塞对象、受影响动作和可执行的恢复步骤。旧操作失败与本次查询是否成功分别表达。
- 为 v2 批次增加显式 `execution_policy=independent`，逐项重新准入，失败项不连带跳过无依赖项；省略策略及旧批次维持 `stop_on_error`。独立模式的规范 Agent/Chat 多工具调用按动作依赖继续，聊天审批保留。
- 使用已有证据惰性修正历史拒绝的分类，保留原始回执、请求哈希及未知订单；不自动重发原单、不补执行旧批次尾部、不自动撤销其他保护单。

## Capabilities

### New Capabilities

无。准入与恢复归入现有独立退出及交易工具能力。

### Modified Capabilities

- `independent-position-exits`: 动作依赖准入、维护隔离、明确拒绝的恢复、历史周期诊断和一致的状态展示。
- `trading-tool-contracts`: 共享准入回执、查询与交易结果分离、显式独立批次策略及规范工具轮次的逐项执行。

## Impact

涉及 `backend/utils/independent_admission.py`、`independent_exits.py`、`trade_receipts.py`、`trade_recovery.py`、`independent_cycle_recovery.py`、证据持久化及 scheduler 维护入口；同时涉及规范工具/schema、batch、Agent/Chat 调度、MCP 适配与 `frontend/src/components/DecisionMessages.jsx`，更新 README 与恢复文档及离线回归。

兼容性：原动作字段、操作身份、fixed/all 和普通/条件单语义保留；新增策略与回执字段采用显式能力声明和添加式迁移。**BREAKING（行为）**：内置独立模式规范工具轮次不再因一次明确失败一律停止所有后续调用；仅明确声明的前置依赖未满足、具体硬约束不满足或本次必需执行证据未核实时阻止对应项。旧批次默认与非独立交易模式不改变。

不包含交易策略/阈值调整、新交易所、真实下单验证、线上自动修复、推理参数诊断或取消交易所硬性约束；不引入强制放行开关。本次仅生成规划文件。
