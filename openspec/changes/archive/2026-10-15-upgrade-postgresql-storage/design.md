# Design

## Context

范围见 proposal.md。用户已明确选择 PostgreSQL 空白建库，只导入现有配置包，不迁移 SQLite 历史。本次不解决另一变更正在处理的模型回执、记忆输出、校验或同步策略。

已检查到的存储耦合如下；数量随并行开发变化，实施以届时基线为准：

| 现有入口/机制 | 升级需要处理的内容 |
| --- | --- |
| `database.py:get_db_conn`、`config_store.py:_get_conn` | 分离的 SQLite 连接、不同的提交语义、MCP 短等待预算 |
| `database_schema.py`、各 store 的初始化方法 | 散布的建表和增量改表；已有 100 余处 CREATE TABLE 语句，不只启动文件中的表 |
| `stats_service.py` 等直接连接 | 绕过统一连接入口，SQLite 日期函数和按位置/名称混用的 Row |
| `rowid`、`lastrowid`、`PRAGMA`、`INSERT OR IGNORE/REPLACE` | 游标、插入身份、元数据、冲突处理及写入锁语义 |
| `protection_scan.py`、`execution_plan_index.py` | SQLite 触发器、来源行身份、持久分页游标及派生索引 |
| `execution_ledger.py` | 临时表、快照重建、`PRAGMA data_version` 的发布前比较 |
| `sqlite_blob.py`、`mcp/paper_storage.py` | 按字节读取及分页，不能改成无界拉取完整 payload |
| `management_lock.py` | OS 锁目录从 `DB_NAME` 推导，Web/scheduler 依赖同宿主共享卷 |
| `chat_graph.py` | 独立 `SqliteSaver`、检查点文件及手写会话删除 SQL |
| `config_store.py`、`config_service.py`、`mcp/transfer.py` | version=1 包、配置事务 hook、运行快照、Prompt 文件和 MCP 凭据 |
| 数据库维护及导出服务 | SQLite 在线备份、文件大小、WAL、VACUUM、上传副本分析 |
| Dockerfile、部署文档、发布脚本 | 当前无仓库 Compose，烟测按单个 SQLite 应用容器构建 |

## Goals / Non-Goals

**Goals**

- 全部运行读写走 PostgreSQL；旧配置包通过原入口恢复配置，重建容器后继续可用。
- 显式管理表结构版本，确保初始化、事务失败、并发和恢复可测试。
- 保持当前有效业务接口及数据含义，把数据库差异留在持久化实现中。
- 交付实际可演练的首次切换和日常更新步骤，包括备份与回退边界。

**Non-Goals**

- 不实现历史搬迁、双写、SQLite 运行兼容层、MySQL、多机集群或高可用。
- 不借换库改变数量计算、交易所范围、管理权规则、同步时机、模型调用或重试策略。
- 配置导入本身不恢复旧仓位/挂单的管理历史，不替用户平仓或撤单；后续执行中的既有 exclusive_scope/visible_first_claim 规则保持不变。
- 当前执行已批准的实现；归档发版和生产 rollout 分别按后续请求执行。

## Decisions

### 1. 使用 PostgreSQL 原生驱动，不模拟 SQLite

使用 Psycopg 3 与有界连接池，保留现有 store/service 分层，逐一将 SQL 改为 PostgreSQL 方言。统一入口拟放在 `backend/storage/`；不通过正则替换 SQL、不伪造 `sqlite_master`、`PRAGMA` 或 `sqlite3.Connection`。

相较全面引入 ORM，此方案减少同时重写数据访问模式的范围；相较 SQLite 兼容包装器，可显式审查锁、事务和游标差异。使用 `DATABASE_URL` 作为唯一运行连接配置，明确只支持 PostgreSQL。SQLite 库只保留在旧上传副本只读分析和旧配置样本生成测试中。

每进程池在应用生命周期创建/关闭，不在模块导入时连接。普通业务池与检查点池合计计入进程/服务器连接预算；获取连接、建连、SQL 和锁等待不超出调用已有预算。连接关闭或归还前清理未提交事务，异常连接丢弃，连接凭据脱敏。保留原连接上下文的显式 commit 语义，不因 Psycopg 默认上下文自动提交而意外提交旧代码原本会回滚的写入；新增事务单元单独声明提交点。

捕获 PostgreSQL 错误后先回滚或回滚到明确 savepoint 再继续；不照搬 SQLite 的“捕获异常后继续使用同一事务”。现有数据库错误分支改为存储异常分类，并映射回既有调用契约，不把断库当作空结果。异步入口继续将阻塞 I/O 放在既有受控 worker 中。

### 2. 空白库基线与显式版本迁移

采用编号 SQL 迁移文件、版本/校验和记录及一个迁移 CLI，单库迁移锁保证一次只有一个迁移者。迁移锁仅用于部署阶段，不作为运行期全库写锁。基础迁移覆盖所有运行表、唯一约束、索引和必要触发器；废弃的历史 SQLite 改表步骤不在新库重演。CLI 不导入 FastAPI 路由、MCP server 或会提前访问业务表的全局配置单例，确保空库引导能够独立执行。

迁移命令先执行应用结构，再执行已锁定版本检查点库的 setup，分别记录成功阶段。检查点 setup 的幂等性按其实际实现验证，失败不能把整体迁移标成成功。Web/scheduler 启动只检查版本及连接，不执行竞争性 DDL；普通请求不再建表。重复执行当前版本为空操作，校验和不一致明确失败。

不让首次启动扫描并拷贝 `trading_data.db`、WAL 或 `chat_checkpoints.sqlite`。旧路径变量不再决定运行存储，文档说明其退役用途；既有配置 JSON 的 env 白名单不扩大为能覆盖目标数据库连接。

### 3. 类型、身份与查询逐项映射

| SQLite 用法 | PostgreSQL 设计及验收重点 |
| --- | --- |
| `INTEGER PRIMARY KEY AUTOINCREMENT` / `lastrowid` | `BIGINT GENERATED BY DEFAULT AS IDENTITY` 与 `INSERT ... RETURNING`；保持 API 身份类型 |
| 隐式 `rowid` | 需要扫描身份的表增加显式稳定 `storage_id`；业务复合主键仍唯一，调用者明确选列，不用 `ctid` |
| 毫秒 INTEGER、REAL | 毫秒及累计计数用 BIGINT；原浮点计算用 DOUBLE PRECISION，避免误用 PG 的 32 位 REAL 改变精度 |
| 文本时间、整型布尔 | 首轮保持现有输出格式与编码语义；日期聚合显式处理北京时间，不顺带迁移时区或改计算口径 |
| JSON payload 与 `json_extract` | 保存原文本/字节语义，必要查询显式转换 JSONB；不为查询方便重排参与指纹的原始 JSON |
| `INSERT OR IGNORE/REPLACE` | 明确业务冲突键，使用 ON CONFLICT；逐处确认更新字段与身份保持，不以 delete+insert 实现替换 |
| `PRAGMA table_info` / `sqlite_master` | 固定结构通过版本迁移管理；维护与只读诊断使用 PostgreSQL catalog |
| 问号参数和标识符拼接 | 值用驱动参数绑定，动态表/列限定现有允许集合并用标识符组合 API |

`BIGINT` 自增值不保证事务提交顺序。对只前进一次的持久扫描游标，不能仅把 rowid 改成 identity 后沿用 `id > last_id`：较小 ID 的迟提交可能被永久漏掉。按各扫描源原有范围使用事务内更新的来源 revision/待处理记录，以及已有去重逻辑；终止扫描前验证来源版本，变化时按原覆盖范围重扫/补扫。所有写入者（含更新、删除和后台写入）必须参与。对每轮归零的循环扫描保留该策略，测试迟提交和更新旧行可达性。revision 是内部一致性元数据，不引入新的交易重试。

SQLite BLOB 分段读取改为服务端字节长度及字节切片，文本使用明确 UTF-8 编码，保持 offset/length、返回编码和已有内存预算；普通分页用服务端游标或受限 fetch，不无界 fetchall。二进制检查点使用 BYTEA。

### 4. 并发事务与金融执行协调保持原责任

逐个审查 `BEGIN IMMEDIATE` 的业务原子单元。已有行用 `SELECT ... FOR UPDATE` / 条件版本更新；“尚无行”的唯一受理、资金范围、配置替换用唯一约束和范围级事务锁，锁顺序固定。配置快照与同一 transaction hook 下的 MCP 导入共用事务。数据库连接池不能自动重跑包含交易所调用的函数。

单机双容器部署保留 `management_lock.py` 的 OS 范围锁，只把目录从 SQLite 文件路径改为显式共享 `DATA_DIR/.management-locks`。其生命周期仍绑定真实 worker，不因调用者超时释放。这样避免在外部网络调用期间持有长数据库事务，也不在本次升级中引入断线即释放的会话锁替代机制。持久管理权和 unknown 操作仍在 PostgreSQL；OS 锁释放不等于交易未提交。该方案不声称支持多宿主部署。

历史重建的 `data_version` 改为按原账户/标的来源记录的 revision：在一致读快照内捕获版本并生成临时结果，发布时锁住同一来源版本、比较后原子替换；变化则保留旧完整结果。相关来源写入必须在同一事务更新 revision。无关范围写入不再触发全库版本冲突，但查询内容和发布完整性不变。

保护活动投影采用 PostgreSQL 触发器与源表同事务更新，保持现有失效/不完整标志及预算语义；不从残缺 JSON 推断成功。业务计算、原操作身份、提交结果未知以及后台核验流程沿用集成基线。

### 5. 保持配置导入契约，持久化包中已有内容

保留 `/api/config/full-export`、`/api/config/full-import`、version=1、现有请求包装与返回计数。复用现有规范化、验证、账户 guard 和 MCP transaction hook；包含密钥的包在目标当前 `CONFIG_MASTER_KEY` 下加密，无密钥包沿用已有处理，不发明默认凭据。

既有配置替换、MCP 导入失败及运行快照回滚路径用 PostgreSQL 回归。验证完成前不修改 Prompt 或 env 文件；文件写入失败须真实报告，不宣称整体成功，不扩展为全新跨文件分布式事务需求。计价写入纳入明确事务/阶段，失败状态可核对。

导入 Prompt 目前硬编码代码目录，而页面的 `prompt_dir()` 已支持 `PROMPT_DIR`/`DATA_DIR`。将导入与所有实际消费者统一到既有目录解析规则，Docker 使用共享 `/app/data/prompts`。保留包内已有文件名及校验规则，不用升级覆盖用户 Prompt；验证 Web 和 scheduler 重启后读到相同文本。

Docker 常规导入使用现有默认 `write_env=false`：管理员在宿主 `.env` 中设置目标安全密钥。`write_env=true` 兼容行为需回归并在文档说明只写入指定 env 文件、需要重启且不覆盖容器进程环境；不能将它误称为完成宿主 Compose 配置变更。首次导入前设置目标密钥，之后保持稳定。

MCP 包只恢复已有导出项。OAuth clients/grants 与访问/刷新令牌不在既有导出中；首次切换需按既有流程重新连接授权。`install_mcp()` 在启动构造路由时读取 public_url，因此导入后受控重启 Web，再验收 issuer/resource 和授权；不承诺导入即时改变这些路由。日常同 PostgreSQL 卷更新保留新版生成的 OAuth 状态。Paper 配置/Key 与 Paper 账户账本不同，不能把导入前者当成恢复后者。策略配置内原有初始金额/持仓参数保持原义。

### 6. 聊天检查点与数据库运维

使用 `langgraph-checkpoint-postgres` 的 PostgresSaver，对齐当前 LangGraph 版本并锁依赖。检查点使用同一 PostgreSQL 数据库的独立 schema，独立池按库要求配置；setup 在部署迁移阶段执行。替换 `SqliteSaver` 及直接遍历 SQLite 表删除线程的实现，验证新会话消息、stream、interrupt/resume、删除和进程重启。

数据库导出保留认证和下载 ticket 路径，输出 PostgreSQL custom-format dump（`.dump`，明确媒体类型），应用镜像安装与目标 PostgreSQL 主版本兼容的 pg_dump 客户端。临时文件流式返回并清理；子进程通过安全环境/凭据文件连接，不在命令行或错误输出泄露 DSN。整个库的 dump 包含应用和检查点 schema；Prompt、宿主 env 与密钥另行备份，数据库 dump 不伪称包含它们。

当前库诊断读取数据库/关系大小和版本；没有对应 PostgreSQL 含义的 SQLite WAL 文件/空闲页指标标记不适用。前端区分运行 PostgreSQL 与上传 SQLite 副本。旧 SQLite 上传分析保留只读入口，不接受为配置恢复方式。

清理继续使用原允许表、任务范围、预览令牌、备份与删除顺序；用稳定身份和短事务锁保证令牌复核到删除期间的目标集合一致。空间回收采用显式 PostgreSQL 维护操作，沿用用户主动操作，说明实际锁影响；不后台自动执行全库压缩，不宣称普通 VACUUM 一定缩小文件。恢复通过隔离 `pg_restore` 演练，不新增未经请求的线上一键恢复 API。

### 7. Compose 与发布入口

新增仓库 Compose，常驻服务名为 `web`、`scheduler`、`db`；同一应用镜像引用用于 Web/scheduler，一次性 `migrate` 入口复用该镜像。目标先固定 PostgreSQL 17 主版本，实施时固定已测试补丁镜像/digest，不用数据库 `latest`。数据库数据挂载独立命名卷，5432 默认仅容器内部可达；应用仍共享 data 卷存放 Prompt、锁和必要文件。

`.env` 明确数据库账号、密码、数据库名和应用连接；构造连接时正确处理特殊字符，不让 Compose 展开或日志泄露密码。部署命令只展示占位值；使用同一个固定项目名/Compose 文件，防止工作目录变化创建另一套空卷。首次切换使用新的应用 data 卷，不因挂载旧卷触发历史导入，保留旧卷供回退。

默认 Web 不带 scheduler；首次只启动 db/migrate/web，导入完成后才启动唯一 scheduler。不能只设置 `RUN_SCHEDULER_IN_WEB=false` 就声称所有后台维护已关闭；首次 Web 阶段通过既有任务暂停/维护开关确保导入的启用策略不提前运行，并核验实际启动路径。不改变配置包中原 enabled 值。

更新/备份脚本拟放在 `scripts/`，提供 Linux shell 入口及纯 Compose 手动等价步骤。它们不自动触发发布或连接生产。沿用已有容量 profile，测量三容器及连接池/维护峰值，不猜测目标主机容量；调整 `scripts/release-archived-change.ps1` 的隔离烟测为临时 PostgreSQL 网络/卷，实际 Git/Docker 发布仍只在归档发版流程执行。

## Migration Plan

### 首次从 SQLite 切换（仅配置）

1. 旧实例导出包含所需密钥的配置 JSON，并保存旧应用镜像引用、env 和数据卷；这里的“丢弃历史”是新库不导入，脚本不删除旧库。
2. 停止旧 scheduler/Web 和其他使用旧实例提交交易的客户端，确认不存在新旧执行者同时运行。若仍需旧本地维护责任，先由用户按既有管理流程处理再切换；本计划不自动取消挂单或认领仓位。
3. 部署新版 Compose 和宿主 env，设置新数据库连接及稳定安全密钥，启动 db 并执行应用/检查点迁移。
4. 仅启动无调度/交易维护执行的 Web，登录，使用原配置导入入口且默认不写 env。核对配置数、引用、密钥、Prompt、计价及 MCP/Paper 设置；保持同一宿主 env 重启 Web，再验收 MCP 发现地址并重新连接授权。
5. 核对健康和只读调用、确认旧服务已停，再启动唯一 scheduler。旧历史不出现在新界面；新历史从此开始。

### Docker push 之后的日常更新

更新脚本遵循以下流程，实际命令及已验证边界见 `docs/DEPLOYMENT_GUIDE.md` 与验收记录：

1. 在服务器固定 Compose 目录选择应用版本（优先不可变 Git 标签/digest），`docker compose pull web scheduler migrate`。
2. 保存旧镜像和结构版本，停止两个应用服务，确认停止成功；db 继续运行。
3. 导出 PostgreSQL 备份和应用 data/env 快照；失败即停止，不执行迁移。
4. `docker compose run --rm migrate`；成功后先 `docker compose up -d --no-deps web` 并验证数据库/应用健康，再启动同版本 scheduler。
5. `docker compose ps`、Web health 和双容器日志核对通过才报告完成。更新不拉取/替换 db 主版本，不使用 `down -v`，不需要删除数据库容器。

### 回退

- 新实例尚未执行新交易时，可停止它并按保存配置恢复旧实例；旧服务接管前仍按现有规则核对交易所当前事实。
- 已有新交易时，不能拿旧 SQLite 或旧 PG 备份覆盖事实。优先回退到与当前 PG schema 兼容的应用镜像，或修复前进；不提供无条件自动 downgrade。
- 数据恢复先在隔离数据库验证。数据库主版本升级是单独运维动作，不纳入每次应用 push。

## Risks / Trade-offs

- [SQL 分散，遗漏隐蔽 SQLite 路径] → 全量静态清单加真实 PostgreSQL 集成回归，SQLite 上传分析作为显式保留例外。
- [写锁消失导致竞争] → 按业务范围审查每处读改写，双进程测试同 ID、资金预留、配置导入与计划版本冲突；不靠全库锁掩盖问题。
- [identity 不等于提交顺序] → 持久扫描测试迟提交、旧行更新和重启；来源 revision 与原分页完整性联合验证。
- [断库发生在交易所 ACK 之后] → 注入数据库故障的假交易所测试，保留原操作身份和既有未知语义，不自动重发。
- [额外数据库/连接池增加内存] → 三容器总预算与既有 profile 实测，不能把换库宣称为 token 或 OOM 问题已解决。
- [导入成功但 Prompt/env 随容器丢失] → 使用共享 data 目录，宿主 env 单独维护，重建后做配置 round-trip 验证。
- [与正在开发的记忆/执行简化重叠] → 本变更先独立建计划和迁移底座；实施共享文件前基于其实际完成版本集成，不恢复已删除的校验/投影链路。

## Validation and References

真实 PostgreSQL 集成测试是发布条件；SQLite-only 单测通过不算升级完成。先测空库/重复迁移/导入，再测同范围并发和故障，最后测 Compose 重建及 dump/restore。交易所与模型均用隔离假依赖，不用实盘写入验证数据库。

实现参考 [Psycopg 事务](https://www.psycopg.org/psycopg3/docs/basic/transactions.html)、[连接池](https://www.psycopg.org/psycopg3/docs/advanced/pool.html)、[PostgreSQL identity](https://www.postgresql.org/docs/17/ddl-identity-columns.html)、[锁](https://www.postgresql.org/docs/17/explicit-locking.html)、[LangGraph PostgreSQL 检查点](https://reference.langchain.com/python/langgraph.checkpoint.postgres) 和 [Compose 容器重建](https://docs.docker.com/reference/cli/docker/compose/up/)。版本/兼容性在实施锁定依赖和容器验收时记录；这些参考不扩大本次业务范围。
