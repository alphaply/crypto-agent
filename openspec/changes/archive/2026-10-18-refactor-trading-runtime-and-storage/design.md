# Design

## Context

见 proposal.md。当前是原生 psycopg PostgreSQL，scheduler 使用进程内 futures，容量失败直接写 SKIPPED_CAPACITY；旧 strict_owned 与共享策略并存。独立退出的完整成交发现和快速当前观察分支需要一致处理外部事实。现有 v3 工具与旧入口已经共用部分服务，但开仓 guard 多层重复。

## Goals / Non-Goals

统一职责与已确认行为，保留公开接口、原始交易身份及全部现有数据。无需更换数据库驱动/框架，不新增交易所、默认资金、统计口径、多机调度或停机时槽回填。本次用户承担完整验收，只执行聚焦小测试、语法及构建检查。

## Decisions

- 新增持久队列 Store，短事务原子领取，运行名额绑定真实线程生命周期。队列分页不等于丢弃上限。每任务串行，跨任务最早可运行优先；新闻身份和原定投周期随队列保存。
- 配置生命周期统一取消未开始项；出队再次校验作用域并读取最新配置。仅未启动项重启后继续；已启动中断不整轮重放，原金融账本负责核验。
- 管理策略归一化，外部观察与维护意图区分。独立模式人工全平/重开更新周期及订单事实，不隐式清理；显式 Agent 平仓的原有执行结果及清理身份保持。强制附带保护使用已保存目标而不是观察到的外部目标。
- 重复入口校验通过单动作作用域或共用执行服务收敛，仍在实际写入前取得必要最新事实；不能使用跨动作缓存跳过金融校验。旧工具及 MCP 继续走原权限和幂等边界。
- PostgreSQL 按业务 Store 统一连接/事务及批量统计；数据库初始化不混入隐式历史删除。保留金额、时间、空值和来源语义，不重算原数据。
- 前端抽取运行状态及展示组件，明确当前运行、待运行及历史结果；其他模块只做有依据的职责拆分和重复逻辑收敛。

## Risks / Trade-offs

- 全量排队可能积压 → 持久化、按批读取并展示数量，不暗中超时或合并。
- 网络提交与数据库事务不能原子提交 → 保留既有原操作身份、unknown 与后台恢复，禁止换 ID 重发。
- 历史配置或不完整成交证据 → 保留原始事实，限制实际依赖，不填默认值或伪造归属。
- 用户不要求完整测试 → 如实记录聚焦检查及未执行的完整验收，不把 Docker 构建当完整验证。

## Migration Plan

追加编号 SQL 迁移，既有迁移不可重写。仅增加队列及归一化配置，不清空历史。构建 frontend/dist 与 Docker 镜像并推送现有仓库；生产升级仍走原备份/迁移流程，本次不重启生产。
