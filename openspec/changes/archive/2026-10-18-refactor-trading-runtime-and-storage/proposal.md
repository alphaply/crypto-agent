# Proposal

## Why

现有交易入口已统一，但底层仍有多代管理策略、重复准入和跨层数据库逻辑。容量不足会丢掉调度轮次，人工外部操作也可能触发不符合独立退出意图的残单清理。本变更落实 2026-10-18 逐项访谈后用户确认的重构方案。

## What Changes

- 调度触发持久入队，按最早可运行项执行；同策略不重叠，不超时丢弃、不合并，定投保留逐时槽身份和预算。
- 排队项运行时使用最新配置；暂停、删除及交易范围变化取消未开始项。界面分别展示当前运行与排队。
- 旧管理策略统一为授权范围共管，旧工具入口保留并复用内部执行链；必要权限、当前数量、交易所约束、幂等与未知原单核验保留。
- 独立退出的人工变更只更新真实状态和记录，不自行撤单、补仓或缩量；下一轮 Agent 可继续决策。强制止盈止损按系统最新保存目标维护，Agent 和已登录前端均可调整。
- PostgreSQL 数据访问、事务及统计查询收敛，保留全部数据、原来源、收益口径与历史身份；其他后端及前端模块按职责拆分去重。
- 用户已明确授权实施及 Docker build/push；只做小范围测试和构建，不执行完整验证套件，不以构建代替完整验收。

## Capabilities

### New Capabilities
- `durable-agent-queue`: 持久调度队列、顺序及配置生命周期。

### Modified Capabilities
- `visible-position-management`: 旧配置统一共管，区分独立退出观察与系统目标维护。
- `independent-position-exits`: 外部平仓不隐式授权周期残单撤销。
- `runtime-resource-capacity`: 明确已受理策略、新闻和定投持久队列不合并、不超时丢弃，保留实际运行数与内存工作集限制。

## Impact

涉及 scheduler/news triggers、配置保存、交易工具/管理/保护服务、PostgreSQL migration/store、统计和前端运行状态。沿用现有单宿主 Web + 唯一 scheduler，不增加外部数据源或多机执行。既有未归档变更及无关本地文件保留。本次交付镜像，不操作生产容器。
