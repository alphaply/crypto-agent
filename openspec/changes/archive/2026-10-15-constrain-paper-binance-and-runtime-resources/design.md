# Design

## Context

动机及现场证据见 `proposal.md` 的 Why。故障日志由用户提供，本规划没有重新读取服务器；本地源码、已发布镜像与正在运行的容器必须在后续报告中分别记录。10-14 的断联不能写成已证实的 OOM。

当前实现有三条相互放大的路径：

- `backend/mcp/paper_market.py` 的 search 会扩展到四家交易所；resolve_quote 在默认场所失败后跨场所发现和报价。market_type 未指定时还会分别加载 spot/swap。PaperSettings、兼容工具、后台撮合都可携带旧 exchange，修改搜索函数不能形成完整边界。
- `backend/mcp/exchange_runtime.py` 缓存完整 CCXT 目录并在写入、读取时深复制；协调器按凭据版本积累。`backend/utils/market_data.py` 的非 MCP 客户端还有独立 load_markets 路径，scheduler 的保护客户端和流连接也有自己的生命周期。
- scheduler 的 Agent、maintenance、成交同步、保护、记忆及新闻/流连接各自限制线程，但没有进程总量与有界队列保证。Paper maintenance 聚合全部账户/订单，history 与 leaderboard 有先全量读取再过滤/切片的路径；保护 tick 还读取已经结束的计划。

Paper 的订单、cash、debt、margin、reserved、回执与事件共同决定资金事实。过滤 raw orders 或修改持仓字典后再计算 available_cash，会把旧预留误释放；仅展示 BN 资产后计算完整权益，会损失历史成本和融资含义。当前部署指南的两条 docker run 命令没有资源上限；现有 scheduler-disabled 发布烟测不能证明 scheduler 的容量安全。

用户新增的故障有明确代码对应：`tool_registry._run_trade_tool` 拒绝与可信任务冲突的 config_id；传入的 64 位值与 close 回执 account_scope 相同，后者由账户标识计算，不是任务选择器。当前默认 schema 虽只公布 target_operation_id，旧 schema、回执恢复指引及历史模型上下文仍能引出额外查询。此次修订按用户最新指令移除查询工具，保留任务边界，不放宽冲突校验。

附件旧 close 为 contract_version=2、SHORT 条件市价止盈、requested_amount=0.03；最新本地投影显示 waiting_trigger、filled_amount=0、仓位观察量0.06，不是已平仓。附件原始 JSON 19943 UTF-8 字节、最新投影4320字节，旧 continuation.previous_assessment.rules 复用同一 blocker 十一次。registry 当前只为 v3 执行分支紧凑投影，旧 close 和操作查询返回全量；现有 compactor 又深复制嵌套 recovery/cleanup，对所有重复字段没有统一字节上限。

## Goals / Non-Goals

**Goals:**

- 将场所策略集中到可信 Paper 边界，使所有调用者和后台任务得到同一 BN 范围与拒绝语义。
- 用“原账本 → 来源分类 → 查询投影/维护工作集”分层实现过滤，保持资金核算、原身份及权限边界。
- 让不同工作池共享可测量的进程容量，同时保留角色隔离、关键恢复额度和 Web 轻量响应能力。
- 将容量配置、实际运行值与隔离验收报告关联，使限额有依据、故障可追溯、生产状态不会被本地测试替代。
- 将金融执行与状态更新归执行层，一次模型调用获得当次真实结果，模型不承担调用后核验流程；新旧金融结果和默认界面使用统一有限摘要。

**Non-Goals:**

- 不迁移、清仓、撤销或重定价非 BN 历史资产；不重建资金、不回填交易盈利、不增加 Binance 未被现有引擎支持的产品。
- 不改变实盘各交易所 profile 的授权能力、v3 顺序契约、任务管理权和聊天审批，也不新增默认金融工具。
- 不在本规划阶段改代码、提交或发布；后续 apply 的实现与隔离验收也不包含真实生产 rollout。单独增大 swap、超时或更换镜像不能作为故障修复的验收依据。

## Decisions

### 1. Paper 的 BN-only 是执行域策略

新增共享 Paper venue policy，规范 BN/binance 的既有合法别名，只接受 Binance。在搜索、行情、v3 整批静态校验、隐藏兼容适配器、订单目标解析、配置保存/导入以及撮合/估值/爆仓维护入口执行同一策略，必须先校验再创建客户端或触及资金。explicit 非 BN 与已知非 BN 目标返回明确范围错误；BN 查询失败返回依赖失败/不完整，不跨场所回退。无 exchange 的新请求继承可信 BN 策略，历史行则执行独立来源判定。

发现只加载请求的 BN 市场类型，别名只帮助匹配核验后的 BN 目录；不使用其他交易所结果、地址或 listing hint 证明可交易。上下文、schema、配置页与导出均公布有效 BN 范围，保留现有 USDT spot/linear perpetual 能力和工具数量。实盘继续用自己的 profile 规则。

配置读取分为兼容解析旧存储和有效运行配置两层。旧 PaperSettings 中合法的 okx/bitget/bybit 值必须能读取并保留原配置证据，再投影为当前有效 BN 策略；不能直接收窄存储 enum 使身份、后台核验、HTTP/UI 审计、银行及偏好在身份核验前崩溃。新保存/导入明确非 BN 仍拒绝，公开导出为有效配置；原旧配置只进入受保护审计，不据此推断历史来源。

选择集中策略而非仅删除搜索循环，是为了覆盖直调旧工具、显式参数和后台路径。保留四家配置但“优先 BN”仍允许隐式回退，不满足范围要求。

### 2. 原账本和可见/活跃集合分离

来源分类为 `binance`、`excluded_venue`、`unresolved_origin`；使用原资源/周期相关的原订单、成交及不可变回执等可信历史证据。现行 upgrade_account 曾按全局默认或同 ticker 最后事件补 exchange，因此现存历史字段可能已被自动回填，不能仅凭其值为 binance 判定可信。只有可证明由金融写入保存且有可信来源版本的字段可以直接使用；其他情况核对原资源/周期证据，缺失、冲突或无法区分回填时保持 unresolved。不根据现行 PaperSettings、同名 symbol 或当前默认 BN 回填。对账户升级、来源分类与有效策略版本采用幂等增量处理，原始数据和分类证据可审计。

默认账户、挂单、成交/历史事件、竞赛事件和 instruments/maintenance 工作集只包含可确认的 BN 金融资源；与场所无关的借还款/账户事件仍按原权限展示。提供过滤原因、有限汇总与估值完整性，区分“过滤后无 BN 资源”和“读取失败”。单个旧 order/operation ID 在原 namespace/user 权限下可查完整历史事实；操作审计保留父子索引和原状态，不压缩后重编号或改写 stored receipt。

raw cash/debt、全部承诺的 margin/reservation 仍是借还款和新 BN 动作准入的依据；被隐藏订单不自动取消或释放。原账本不经过默认投影再参加资金计算。混合账户的 BN 可见资产可以局部估值，但完整 equity、净收益和 return percentage 不可靠时返回不完整/不可用，榜单排除并解释原因；没有经过核验的独立 BN 成本和融资基线，不生成“BN 收益率”。

新 BN 入场与被过滤旧资源同 symbol/side 时，不能沿现行 exposure 的仅字段匹配合并。为新 BN 资源持久化独立资源身份、可区别的存储 key 与新周期，保留旧 key/ID 和旧数量、成本、margin、周期及预留；已证明的同 BN 活跃资源才按原规则增仓。所有目标解析和维护据可信来源与资源身份选择；若某兼容路径不能独立寻址就目标级拒绝。新成交不得作为旧缺失来源的回填证据。

历史过滤选择逻辑投影而非删除或转仓，既符合“不涉及其他交易所”，又能保留资金与审计。把旧资产按 BN 同名 symbol 定价或把旧挂单直接撤掉，都会改变金融事实。

### 3. 保留原操作恢复，冻结范围外金融效果

整批发现非 BN/无可信来源目标时，首次金融写入前拒绝全部批次；动态余额和目标状态仍在各项提交时检查。已存在的 v2/v3 操作必须先按原身份找到原记录、比对原请求指纹，再区分审计/恢复与新执行，不能先套新默认 exchange 导致指纹变化。

已完成旧非 BN 操作可只读返回原事实；pending/unknown 的范围外项只从持久记录核验，没有权威提交证据时保留未解决状态，不能获取旧场所行情、重放金融写入或自动执行尾项。若子项账户变化和原子回执已持久提交，仅父响应丢失，允许由原 ID 的真实子回执重建已完成事实；冻结的是新金融效果，不是阻止核实旧事实。BN 原操作的恢复也只核验已尝试项。

本次 invocation 没有进入执行就被资源拒绝时明确 busy/`not_started`，不能把该结果覆盖为同 ID 历史父操作的状态；已有已提交或 unknown 父继续保留原状态、指纹和后台关联。本次连权威原账本都未读到时明确原状态不可验证，不据本次未启动推断历史零成交。开始后发生超时、退出或进程死亡则保留已有身份、阶段及未知状态。

选择冻结并可审计，避免“兼容旧入口”绕过新策略，也避免把幂等恢复变成一次新交易。旧客户端若依赖多场所 Paper，需接受明确 breaking error；对原已完成操作的查阅仍兼容。

### 4. 缓存容量包含客户端持有的副本和刷新峰值

建立 MCP 与非 MCP 共用的公开目录模块，在每个进程内按 venue、市场类型、公共端点及影响目录的公共选项分 key 并合并刷新；不以 secret 或凭据轮换作为公共目录身份。缓存只保存经过能力筛选的必要公共元数据及来源/观察时间，减少完整目录深复制；每个可变 CCXT 客户端仍保留自己的必要可变结构、timeDifference、认证和执行状态，不能直接把一个交易客户端共享给不同任务。

Web 与 scheduler 各有进程内缓存和 single-flight，不引入跨容器缓存服务或新的 IPC 依赖。两者独立冷加载、同时刷新和实际副本全部计入双容器/主机预算，验收不宣称部署全局只加载一次。跨容器公共快照可进一步省加载，但增加一致性和故障依赖；当前用小快照、有限副本与明确总预算保持部署隔离。

容量账目同时包含 entry 数、保守估算的 resident bytes、正在初始化客户端的引用、刷新时旧/新数据和解析临时空间，并用实测 RSS/容器 peak 验证估算。TTL 表示新鲜度，不能代替容量上限。相同 key 的冷加载/刷新合并为一次有预算的工作；加载前预留峰值额度，超大响应和目录在有界请求/解析范围内终止或拒绝持久缓存，不能先无界加载再决定淘汰。失败不会把不完整目录当成成功；旧快照若可供查询，必须声明时效，交易准入不使用失效事实。

quote、公开目录、客户端、协调器与 websocket 连接均有数量/字节或活动引用上限及退休清理。淘汰不删除仍保护操作的锁、未知操作关联或执行中协调器；使用引用/租约与退休状态，物理 worker 结束后才关闭/归还。配置删除、停用和凭据轮换需要明确释放无用客户端/连接。独立 per-client 深复制最容易保隔离，但放大峰值；完整共享可变对象节省内存却破坏隔离，因此采用小公共快照加受预算的客户端适配。

### 5. 独立角色池共享进程总准入

为 Web、scheduler 各自建立总容量管理器，所有重任务及嵌套子任务必须获取额度：MCP/public catalogue、Agent、Paper维护、成交同步、保护、记忆、新闻、流连接/订阅。现有角色池仍限制各自并发、避免互相饿死，但总运行额度、每类 queue、等待时间及活动客户端受统一配置约束；同一资源已在父任务计费的顺序子步骤不重复计费，并行子工作须增量准入，避免 worker 等待自己占用的容量而死锁。

额度依据 capacity profile 的测量权重/并发上限，实际容器 CPU quota/affinity 可作为调度约束；不依赖宿主 os.cpu_count 自动放大线程。预算校验失败应在启动/配置提交时明确报错。为后台核验原操作、必要保护和一致性恢复保留不可被新 Agent/新闻工作耗尽的额度；Web 的健康、静态与轻量诊断通路有独立响应余量。总额度包含保留额度，不允许“保留池”额外越过总限。

队列满/压力高时返回 busy 或延后下一轮维护，不自动重试金融写入。future 取消或请求断开不能归还仍在运行线程的额度。长驻 websocket 在整个活动寿命计费；关闭与重连也经过上限和退避。角色池只增加总 semaphore 但仍允许无界排队，不能满足内存预算，故入队前也需准入。压力信号是提前降载补充，硬并发/缓存预算和 cgroup 限额是基础。

### 6. 后台扫描以稳定游标分批推进

Paper instruments、维护、history、leaderboard 和事件轮询从持久存储按稳定 cursor/主键读取有限批次，限制每轮账户/标的/事件数量及耗时；保护扫描只选择需要处理的 active/unknown 计划。过滤可以应用于 workset，但一致性计算仍读取当前账户全部已承诺资源；单项资金事务不被拆成多轮，网络不进入账户事务锁。

批次条数不能约束单个超大 JSON 账户/回执：读取前检查 payload 大小，当前投影用有界存储读取或增量索引。若原账户无法在预算内完成完整资金核算，该账户的新金融动作及维护明确返回资源不足/未处理，保留账本，不能只取部分预留继续执行或无界解析；审计保留原身份及受预算的续读方式。

事件游标允许跨过被过滤历史行，在扫描预算内返回 filtered/count/continuation 状态，空可见页不会无限重复扫描或被当作全量结束；delivery_key、排序、namespace 和通知偏好保持不变。榜单超过扫描预算时声明未完成/使用带观察时间的已完成投影，不能把某批子集当作完整排名。后台任务按稳定进度继续，使用已有按配置去重和身份恢复机制避免重复匹配/事件。

只减少线程数不限制单任务工作集，仍可在一个线程内耗尽内存，因此同时限制输入批次、存储读取和网络响应。

### 7. 测量后确定双容器和主机预算

新增可执行的 capacity profile 与只读采集/隔离负载入口。profile 在跑测量前声明测试环境、最大业务规模、冷/热目录及刷新场景、并发与时长、Web 响应目标、资源上限和接受阈值。先测 idle/典型/并发/持续刷新和配置轮换，再形成推荐的 Web/scheduler memory、memory+swap、CPU、应用额度及安全余量；不把历史 ~1.2GiB RSS 当作推荐限额。

流程分校准与最终验收两轮：校准在已检查主机余量的保守受限环境收集测量，报告可据此产生下一版本 profile；选定最终数值后，冻结该 profile 重跑完整验收。失败的旧报告和阈值保留，不能修改已跑 profile 的限额/SLO 把失败变成通过；校准报告不能替代最终部署配置的验收报告。

报告用主机 RAM/可用 swap、其他进程与系统保留量校验双容器合计；swap 不作为可持续工作内存，CPU 合计须为 SSH、面板、代理及健康响应保留余量。Docker 启动入口、可重复的隔离烟测及部署文档明确设置限制，读取实际 cgroup/inspect 值，核对 memory-swap 的总量含义、宿主可用性及 CPU 限额是否生效。生产启动不应默认为 unlimited；不兼容平台必须显示未生效/不可验证，而非报告成功。

压力/OOM 注入只在与生产数据/凭据隔离的受限环境进行。新 profile 的 isolated Web+scheduler 验收包括峰值、队列、缓存、过载响应、保留额度和死亡后未知操作恢复，不能只测 scheduler-disabled 首页。capacity 报告保留具体镜像/commit/配置/数据规模、实际限制、观测时间和待现场验证项。操作员后续请求 rollout 才把已验证配置应用到真实主机并复验公网。

### 8. 故障证据在重启前后可关联

持续采集进程 RSS、cgroup current/peak/limit、OOM counters、CPU 使用/节流、池/队列与缓存预算、主机 RAM/swap 及工作阶段；容器内读不到的宿主指标由受限只读宿主采集补齐，不可读则报告 unavailable。每次启动关联启动 ID、实际镜像/容器身份、UTC 时间与本地时区显示、配置摘要、worker 类别和已有 request/operation ID。

指标和阶段日志使用有界 buffer、周期性落盘及按容量轮转，外部依赖异常不产生高基数无限记录；采样不能阻塞金融提交或暴露令牌/密钥/原凭据。容器状态在重启后 OOMKilled=false 只表示本轮状态，历史诊断须结合 kernel/cgroup/docker event 和保留的容器映射。报告区分“主机 global OOM”“容器限额 OOM”“仅资源压力迹象”“无故障瞬间证据”，不凭断连或单次 RSS 定因。

### 9. 移除模型操作查询，ACK 后及时返回

从 get_trade_tools_for_mode、CANONICAL_TOOLS/registry 可调用映射、MCP 新旧注册和兼容直调集合移除 get_trade_operation/get_operation；底层 refresh/recover 与原父子映射函数继续供执行层、scheduler 及授权 HTTP/UI 使用。缓存名称明确不可用且不执行原查询。Agent 可写交易绑定为 1 项，只读角色0项；live MCP 为7/6，Paper为10/7。get_trade_records 保留普通订单/成交/历史语义，不增加 operation 查询 facet，execute_trade_actions 也不增加 query 动作。

对所有金融入口使用同一流程：可信任务/profile 注入范围 → 按当前动作所需取证/准入 → 持久意图 → 提交原动作 → 根据权威响应保存回执并返回。ACK 若只证明受理就 returned submitted；若响应本身已证明成交/撤单等请求效果，按原意图报告完成。收到权威 ACK 后不强制再 fetch_order/fetch_positions 才返回，不轮询等待未来成交。可能影响下一已声明动作的真实依赖仍在执行该项前核验，submitted 仍不能满足 completed 依赖；这不是由模型发起第二个核验调用。

将尚未解决的已尝试身份交给有界后台只读核验，复用成交同步、保护及 Paper maintenance 的额度和调度，覆盖 REAL 的不同退出模式、STRATEGY、SPOT_DCA、live/Paper MCP 和旧 v2/无版本记录。核验使用可信 owner/namespace/principal 与持久原 symbol/订单/client ID，不接受模型的 account_scope 充当 config_id。后台失败保留事实与退避，主动更新原回执、当前状态、记忆及 UI；不重复原金融写入、不补跑尾项。必要的已授权周期维护仍遵循自己的规则，不能被核验当成盲重放。

清除提示、工具描述、recovery 文本和模型可见历史投影里的 call get_operation、先查询再继续等指导；默认摘要仅说明状态及系统正在更新。原始历史 JSON 中旧工具字段保留审计，但不再作为模型调用指令注入。用户主动查完整证据走现有受权限保护的 HTTP/UI 详情；这些被动读取不执行交易，也不成为模型执行后的固定第二步。同 ID 网络重传仍按原幂等规则处理，不用重传把查询工具换成另一个名称。

选择彻底退役查询工具，避免仅修 config_id 参数后保留用户明确拒绝的工作流。直接接受账户 hash、默默覆盖冲突上下文或让模型通过 get_trade_records 轮询原操作，都不解决这次要求。

### 10. 新旧金融回执使用有界摘要

在持久完整回执之后、进入模型 ToolMessage/默认 API/UI 数据之前执行统一 summary projection。覆盖 v3、旧 close/open/edit/cancel 及其他金融兼容入口，不能只处理 v3 分支。按字段读取必要事实，不先复制完整 previous_assessment 树；数据库原请求、原回执、版本化后续事实和指纹不重写。

默认单项返回上限为4096 UTF-8字节，1–20项整批为32768字节，测试按实际返回 JSON 文本计量。优先保留全部动作索引/原身份、操作与订单状态、必要当前/旧/客户端身份、fixed/all单位、请求/已知成交/剩余数量、修改阶段、简短错误码及时间/来源。scope 放一次且不向模型暴露可混用的内部账户选择字段；同一数量别名与 position/current_position 只留清楚的一份，fill=0 不能因 falsey 被丢弃。附件典型条件 close 显示提交0.03、已成交0、待触发；仓位0.06只能按原观察时间显示，不能从 ACK 声称最新剩余量已核验。

continuation 只呈现相关未决/失败的简短事实，不携带 previous_assessment、全部规则、重复 scope 或同一个 blocker 的多份副本。默认 blocker 列表有限，长错误、诊断与旧评估移到详情，注明数量/省略范围和原记录引用。整批对共用字段去重、限制账户摘要，并以结构化省略而非截断字符串/JSON满足预算；所有索引、真实状态和身份不能为压缩消失。详情引用不是权限凭据，每次读取重新按原任务或 principal/profile/namespace/user 鉴权；大详情遵循既有读取/解析预算，分块/分页并固定证据版本，不能每页重新取得不同快照。

DecisionMessages 默认用简短结果及系统更新后的同口径状态展示，完整原始和最新 JSON 在用户主动展开时加载。详情的原始版与最新观察版分清；不因 get_trade_operation 的旧查询失败把已受理交易显示成 close 失败，也不把 waiting_trigger 显示成已成交。历史查询/错误留在审计，默认模型不重注入整份双回执。

选择结构化摘要和按需审计，使默认调用长度受限而完整证据仍可追溯；直接删除回执或截断 JSON 会丢失交易身份及状态，不可采用。

## Risks / Trade-offs

- [混合账户隐藏资产仍占用资金，用户可见余额与可用余额差别扩大] → 展示 filtered commitment 汇总与完整性原因，保留原 ID 审计，不通过释放资金改善显示。
- [旧行来源缺失导致更多历史数据被排除] → 仅由原始证据幂等补足，来源不明保持 unresolved；发布说明提前解释默认过滤。
- [CCXT 目录结构与初始化有版本差异，尺寸估计偏低] → 覆盖已锁定依赖的客户端隔离测试和冷/刷新 peak 测量，加载前保守预留，容器硬限额兜底。
- [新增总预算产生嵌套等待或关键维护饥饿] → 父子额度规则、角色保留容量、有限排队、取消寿命和压力下恢复测试；不允许保留池越过总预算。
- [cgroup 限额保护主机但可能杀死 scheduler] → 持久阶段及原操作身份、重启只读核验、合理测量余量；OOM 不触发自动金融重放。
- [日志/指标本身累积占资源] → 固定采样上限、低基数聚合与容量轮转，测试采集器故障和长期运行上限。
- [本地验收容量与真实主机其他服务负载不同] → 容量报告声明平台及主机假设；真实 rollout 时校验余量和限制，未完成现场验证保持该状态。
- [移除查询工具后后台核验责任未接全会使状态长期停留] → 各模式及历史版本自动核验覆盖测试、保留额度/退避及最新事实消费者回归，不以提醒模型调用另一个工具弥补缺失。
- [摘要字节预算掩盖执行事实或旧客户端字段依赖] → 核心状态/身份/数量不截断，诊断注明省略并可授权审计；旧输入和指纹保持，新默认返回精简作为明确 breaking 展示变化。

## Migration Plan

1. 以只读副本制作含 BN、非 BN、来源缺失、混合预留及旧 v2/v3 回执的隔离 fixture；记录升级前原行、资金与指纹校验值。若后续获取现场数据，先脱敏并避免使用真实交易凭据。
2. 增量引入有效 BN 策略、可信来源分类和过滤/估值完整性；保留原始账本与配置证据。旧非 BN 全部退出默认与活跃集合，缺失来源不按新默认回填。重复升级不改变资金、原 ID 或管理者。
3. 接入公共缓存/客户端生命周期、进程准入、有界扫描和持久采集；移除模型操作查询注册/提示，接通全模式自动状态核验及新旧金融摘要/授权详情。更新配置页、工作流和部署示例，执行离线回归与容量 profile，产生报告后选定部署限额。
4. 后续 apply 完成实现及隔离验收后按用户另行请求完成发布。发布烟测绑定资源配置；发布镜像不会更新运行容器。
5. 后续 rollout 请求到来时，记录现场实际镜像/容器/资源预算，备份原数据及限额配置，再更新两个真实容器；核验实际生效限制、资源余量、BN-only 与公网只读路径，并保留明确回退步骤。
6. 回退不恢复旧多场所维护：保留增量来源/策略信息和已验证限额。若旧版本不识别该策略，只可进入 scheduler/金融写入停用的诊断模式；不得让它重新撮合隐藏订单。回退或重启均沿原 ID 恢复，不重置数据库或自动补跑尾项。

## Open Questions

- 具体 memory/swap/CPU、池容量、缓存字节、扫描批次及 Web SLO 数值由第 7 项已定义的容量流程产出；它们是同一契约内的调优值，必须在选定 profile 的验收执行前固定并写入报告。
- 真实主机的 cgroup 版本、swap 约束支持和其他服务基线在用户请求 rollout 后现场读取；不可读或无法满足 profile 时明确阻断该部署配置的使用，不改变 BN 范围及资金保留策略。
