# Proposal

## Why

2026-10-17 的 ETH 工具调用耗时约 889.68 秒，但实际下单请求至交易所回执仅约 78 毫秒，主要延迟发生在下单记录创建之前。当前前置管理流程会同步整理历史订单、反复扫描并长期占锁；工具结果又被多层折叠和内部字段包围，用户难以直接看到操作是否提交成功。

## What Changes

以下均为本轮已确认范围：

- 将全量历史归属整理和收益历史重建移出金融调用的同步路径，避免后台整理持锁拖住下单；保留当前动作必需的权限、目标、持仓数量和并发校验。
- 历史整理改为真正有界、可恢复的后台增量工作；减少逐记录重复数据库访问，普通状态变化不再触发整段历史从头重扫。
- 交易所返回权威成功回执即认定本次提交成功，保存原身份和回执后返回，不追加提交确认查询，不等待挂单成交或历史整理完成。
- 后台照常更新原订单成交、实际持仓和盈亏；这些更新不改变已经确认的提交成功事实，不重复下单或续跑未执行项。
- 交易结果直接展示操作类型、标的、方向、数量、价格和成功／失败；删除该结果区的多层展开、原始 JSON、审计入口、重复数量以及核验说明。
- 用分阶段耗时记录与隔离回归验证，区分锁等待、当前事实读取、交易所请求、回执保存和后台历史工作。

不改变交易策略、订单类型、数量单位、顺序批次依赖及幂等语义；不删除原始证据，不增加交易所或替代数据源，不承诺尚未经测量的线上秒数。此次仅生成开发方案，不实施、不发版、不重启生产服务。

## Capabilities

### New Capabilities

无。

### Modified Capabilities

- `trading-tool-contracts`：明确当前动作不等待历史归属全量整理，权威提交回执不被后续历史/后台工作阻塞或降级。
- `runtime-resource-capacity`：明确历史归属整理的单次工作界限、持久增量进度以及与金融锁的隔离。
- `tool-receipt-presentation`：交易结果改为无需展开的六项精简展示，成功表示本次操作已被接受；移除交易结果区的原始 JSON、审计与核验展示。

## Impact

- 后端：`execution_plan_index.py`、`execution_ledger.py`、`position_management.py`、`position_protection.py`、`independent_exits.py`，以及 scheduler 的执行同步、管理维护和后台回执入口；必要时通过显式 PostgreSQL migration 增补检查点/变更队列。
- 金融入口：核对 `trade_operations.py` 与 `unified_trading.py` 的回执落库和返回边界，兼容新旧入口，不更改请求版本或原操作身份。
- 前端：`ToolResultContent.jsx`、`DecisionMessages.jsx`、`toolReceipt.js` 及实际复用这些组件的运行过程/聊天页面；只读查询工具不纳入交易六字段投影。
- 验证与文档：扩充已有历史索引、管理并发、后台回执和前端 fixture；更新 README 与相关工具/运维说明。使用合成账户和隔离数据库，不以生产交易验证。
- 已有未归档变更 `simplify-memory-and-ordered-execution` 不在本次修改范围；实施时核对交集，保留其独立任务和历史意图。
