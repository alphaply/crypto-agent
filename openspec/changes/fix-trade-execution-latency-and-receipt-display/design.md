# Design

## Context

动机与确认范围见 [proposal.md](proposal.md)。现场调查是只读检查，未执行交易、重启或部署。

### 实现中的实际耦合

- `ExecutionLedger.__init__()` 立即调用 `index_saved_plans()`；`sync()` 在索引不完整时又会推进索引。对象初始化和调用成交同步都会隐式承担历史工作。
- `execution_plan_index._advance_index()` 用 `while True` 持续推进全部阶段。`RUNTIME_SCAN_BATCH_SIZE` 只限制单页；`RUNTIME_INDEX_SCAN_SECONDS` 在现有测试被设置，却没有在此循环实际使用。`test_cross_page_regular_evidence_completes_in_one_call_before_alias_retirement` 还要求一次处理超过页大小的全部来源。
- `_source()`、`_load()`、`_plan_facts()` 与发布阶段按来源及订单逐条查询/写入。多份历史快照包含相同订单，仍反复提取、暂存、登记；数量少的最终唯一订单不代表扫描工作少。
- 来源版本不同会删除当前索引暂存记录与事实，并把游标归零。`0005_ownership_observation_revisions.sql` 已忽略当前计划的纯观察字段更新，但新增 `real_protection_events`、订单变化及其他有效来源变化仍会增加标的级版本。不能把“增加同类过滤”当成完整修复。
- `managed_action.coordinated()`、`management_action()` 等先持有账户级 `RLock`，`ensure_managed()` 的 `_discover()` 又构造 ledger、同步历史。外层阻塞取锁也可能先于内层有界等待，因此只改 `ensure_managed()` 的等待时间不足以覆盖全链路。
- `PositionProtection._save()` 除保存当前计划、登记订单外，还直接重建历史；`IndependentExits._save()` 为退出订单重复登记并可能反复重建。即使关闭 ACK 后读取，同步本地历史处理仍可能留在返回路径。
- `financial_ack_only` 已让部分 ACK 后维护退出为后台待更新，但没有解开上述初始化、前置发现及保存历史耦合。
- 前端 `ToolResultContent` 用通用递归 `details` 展示嵌套结构；`amount` 与 `requested_amount` 均标“数量”。`DecisionMessages` 额外显示审计入口及调用参数 JSON。`ChatPage` 和 `DecisionRunPanel` 复用这些组件。

## Goals / Non-Goals

**Goals:**

- 让前台工作量与当前动作直接相关，而不是随累计历史条数增长。
- 为历史初次整理、后续变化和重启恢复建立真实有界工作及不丢来源的持久进度。
- 成功回执经必要持久化后返回；更新成交/持仓/盈亏与本次提交是否成功分开表达。
- 在运行过程和聊天中使用同一份六字段交易投影。

**Non-Goals:**

- 不移除当前权限、实际目标/数量校验、幂等、共享资源金融写入协调；不改变 open/close/edit/cancel/protect 的能力、价格或数量含义。
- 不把内部 submitted 改成 completed，不改变 depends_on 只接受既有 completed 的规则，也不删去未知原提交身份。
- 不删除历史、关闭正常成交/持仓更新，或用仓位差额伪造成交。
- 不重设计一般查询工具、记忆、交易策略、全站审计权限或资源配置界面，不承诺交易所/模型的固定响应时间。

## Decisions

### 1. 将当前金融事实与历史归属整理拆成独立入口

使 ledger 构造只建立范围和读取轻量检查点；历史整理必须由显式后台推进入口触发。`_discover()` 区分当前资源发现、当前订单原身份恢复、真实基线及历史来源整理。正常金融调用按既有可信账户和授权范围，读取当前持仓、目标、挂单和原操作必要事实并进行准入，不执行全量索引或收益重建。

当前计划写入、原操作/订单身份登记、共享预留和成功回执仍可靠持久化。将 `_save()` 内的历史重建改成同事务登记受影响范围的后台待处理工作，避免任一单腿登记都重建一次全历史。后台失败只留下待处理状态，不覆盖已确认的 ACK。

必要的当前依赖若确实不明，继续按原有目标级错误/未决规则处理；不会把“历史没扫完”当作全账户禁止交易，也不会伪造历史齐全或使用旧仓位代替当前量。首次发现人工资源仍遵守既有当前观察基线语义。

**考虑过的替代方案：** 只调低数据库超时或只删核验文字不能消除同步历史工作；直接跳过全部检查会改变交易权限与数量约束，均不采用。

### 2. 真正分片推进，并使用可恢复的来源变更记录

复用现有容量管理和 scheduler 的维护/恢复调度入口，不新增独立无界线程池。单次历史工作使用生效的行数/字节预算和 `RUNTIME_INDEX_SCAN_SECONDS` 截止时间；在有界原子单元之间保存检查点并退出，不在一个调用里立即循环调自己。数据库步骤也须受剩余预算限制；合法单条来源的处理/发布不能藏一个无界循环。

通过新的显式 PostgreSQL migration 增补按来源类型、来源主键与版本记录的持久待处理集合及扫描检查点。来源变化在同一个来源事务中登记，覆盖新增、更新、删除及作用域移动。worker 按读取的来源版本完成处理，只有版本仍匹配时才清除待处理标记；新变化保留给下一片。

初次建立历史基线采用键集分页和已记录边界；并发变化由持久待处理集合补齐。不把自增 ID 分配顺序当作事务提交顺序，必须处理较小 ID 晚提交及扫描期间旧行变更。后续只处理新增/变化来源，避免标的级 revision 一变化就删除全索引。`ownership_plan_source()` 继续用于识别真正影响归属的投影；相同投影复用提取工作，原始历史一条不删。批量读取大小、元数据和投影，批量登记链接，避免每个重复来源/订单都单独打开连接、提交和重建。

完整性与发布分开：阶段性扫描结果不冒充完整归属；普通/条件单数字碰撞的正向普通订单证据需要覆盖相关来源后才允许退休别名。发布前核对受影响来源版本与已有当前链接，旧历史不能覆盖较新的权威订单事实；未完成的新一代整理不删除已确认链接。历史变更或删除需要重算受影响投影及其引用，不能仅追加后永远忽略修正。

**考虑过的替代方案：** 只加每页 LIMIT 仍然会一次跑完；只记最高事件 ID 会漏掉更新及晚提交事务；只忽略观察字段不足以应对真实新增事件。三者均不能作为本次最终方案。

### 3. 历史锁与金融锁分离，保留短时原子发布

后台扫描/解析不在账户金融 `RLock`、金融文件锁或长期数据库事务中执行。索引使用自己的非阻塞工作权和持久版本协调，Web 与 scheduler 争用同一工作时一方退出并下次续接。发布只保留必要的短事务与相关范围版本检查；账户/标的/方向的金融互斥继续遵循原模式。

统一检查 `managed_action`、`management_action`、`ensure_visible_management`、`ensure_managed`、ledger 初始化及 `_save()` 的锁顺序；不允许外层无期限取锁绕过内层预算。金融锁仅覆盖实际需要一致性的当前观察、准入、持久预留及金融写入；并发金融动作仍遵守既有有界冲突处理。历史重建先准备结果、再短时发布，冲突时保留原进度而非持锁重跑全部来源。

**考虑过的替代方案：** 整体删除锁会造成并发超量退出、共享预留和订单版本竞争；把原长扫描整体丢到新线程仍会占相同锁，均不采用。

### 4. 权威 ACK 是本次提交结果边界

复用原 `run_once`、父子身份与 `financial_ack_only`，删除为“允许返回提交成功”追加的 GET/轮询和同步历史计算。收到合法受理回执后保存原意图、客户端/订单身份和回执并返回；ACK 已有的成交事实保留，无证据不补零。

后台只更新原已尝试订单的实际成交、持仓、盈亏和增量证据。原提交成功不因稍后读取失败而变成提交失败。网络超时且无权威 ACK 仍沿用现有 pending/unknown 与原身份恢复，不把超时当成明确拒绝，也不换 ID 重试。现货、附带保护与模拟入口只做对应单次回执返回回归，不能扩张本次实盘历史索引改造到无关账本重设计。

**考虑过的替代方案：** 把 submitted 全部改为 completed 会改变后项依赖与成交含义；把所有异常都显示/记录为失败会掩盖可能已提交的原订单，均不采用。

### 5. 交易结果使用专用平铺投影

在 `toolReceipt.js` 中提取纯投影供运行过程和聊天复用；以可信工具名、回执版本/动作结构区分交易与一般查询，避免任意对象被误识别为交易。按动作 index 展示每项，不用父批次状态覆盖子项，不递归铺开原始回执。

| 展示项 | 取值原则 |
| --- | --- |
| 操作类型 | 原动作映射开仓、平仓、改单、撤单、保护；兼容原入口动作 |
| 标的、方向 | 回执或同一原操作的可信请求字段；缺失不猜测 |
| 数量 | 当前操作的委托量；edit 对应目标未成交量；显式 all 显示全部，不以 filled=0 覆盖请求量 |
| 价格 | 该操作实际回执/原请求中明确存在的限价或触发价；两者并存时在同一价格区域标明类型；市价缺价不编造 |
| 结果 | 有权威接受/完成证据显示成功，明确失败或未执行显示失败；成功只表示本次操作获接受 |

执行中或无权威结果时不制造成功/失败终态；保留原有未决事实供后台继续更新，页面不铺开核验原因和恢复树。本次不新增未知状态的交易决策或自动重试。旧纯文本只直接显示可读精简文本，不能靠字符串猜字段或伪造成功。

`ToolResultContent` 对交易使用这一投影，移除交易的完整结果/原始 JSON；`ToolReceipt` 不再附带交易审计展开；`DecisionMessages` 的同次交易调用不再展开参数 JSON 或重复状态卡片。检查 `ChatPage` 参数传递，使聊天和 `DecisionRunPanel` 的实时/历史记录都一致。一般查询工具保留已有展示行为，现有后台证据与授权审计 API 保留。

主规范目前要求交易结果显示已提交/已成交/待确认并可展开原始详情，与本次明确要求冲突；通过两个 MODIFIED requirement 完整替换交易展示规则，一般查询行为保留。模型回执中的原状态不跟着界面二值化。

### 6. 验证关注工作边界与实际调用，不只看页面文字

- 扩展现有 PostgreSQL fixture：生成不少于现场量级的合成历史，包含重复快照、普通/条件同数字、晚提交、更新/删除、并发写入及重启。替换要求一次扫描完毕的旧断言，保留其“别名退休不得早于必要证据”的核心保护。
- 用可控后台闸门阻塞历史 worker，验证前台能在闸门释放前完成合法当前动作；断言前台没有调用全量索引/历史重建，ACK 后没有提交确认 GET。这比仅比较两次墙钟时间更能防止耦合回归。
- 用查询/处理条数计量验证单片上限、无变化再次调用的固定小工作量、单次新增来源不会重新读取全部历史；所有来源最终可完整覆盖。另在隔离真实 PostgreSQL 环境记录实际耗时与 SQL 数量，不能只靠 mock 声称性能通过。
- 扩充分阶段日志：前台锁等待、当前事实读取、交易所请求、ACK 保存、返回；后台扫描、处理条数、检查点和发布分别计时。使用 monotonic 时钟，脱敏，不输出凭据或完整计划/回执树；操作关联放日志，不作为无界指标标签。
- 复用 `test_single_call_execution.py`、`test_background_receipts.py`、管理/共享账户/恢复及统一批次测试，验证失败、未知、部分成功和重放均不重复金融写入。前端 fixture 验证桌面/窄屏、中英文、已接受零成交、混合批次和旧文本；运行前端构建并保存截图。
- 技术验收预算在隔离运行前固定并写入验证记录，不以生产账号下单、不用尚未测得的“几秒内”作线上保证。

## Risks / Trade-offs

- [移除同步历史后出现旧链接与新事实竞争] → 当前目标直接按权威事实校验，短时发布执行版本检查，旧历史不能覆盖较新提交；别名碰撞和缺口保留原保守处理。
- [索引变更队列漏掉晚提交或旧行更正] → 来源事务内登记、按源版本清除、初始扫描与变化集合共同覆盖；专项 PostgreSQL 并发和重启测试验证。
- [后台积压长期不收敛] → 用既有容量调度分片推进、去重并记录最老待处理/游标进展；成功 ACK 返回不依赖队列清空，必要成交与持仓更新继续获既有容量。
- [缩小锁范围损害金融一致性] → 不整体删除金融锁，保持相同账户/标的/实际方向的预留和版本检查，跨进程并发退出测试必须通过。
- [简化展示误导为成交成功] → 六字段中数量取委托量，成功只映射操作受理事实；内部订单/成交状态和模型契约保持原意。
- [纯文本老记录缺字段] → 保留可读精简文本，不编造新结构；不为了六列齐全增加新查询。
- [实际交易所慢或数据库保存慢] → 分段记录实际阶段；本次消除历史工作拖慢，不能用单次现场 78ms 推断所有交易所请求都快。

## Migration Plan

1. 实施阶段新增兼容性 PostgreSQL migration，建立来源变更记录与新检查点；先启用变更捕获，再允许有界初次整理，避免迁移窗口漏来源。保留原订单、成交、来源和操作表及原身份。
2. 切换所有前台入口到当前事实路径，再由现有后台调度推进新整理；同数据库运行的 Web/scheduler 使用兼容版本，避免旧初始化继续同步扫历史。来源变化若尚未就绪，只影响依赖该具体事实的动作，不扩为无关交易阻塞。
3. 隔离验证通过后更新 README 与相关说明，按后续用户指令进行 apply、归档/发布或生产上线。本次 propose 不执行这些动作。
4. 回退保留新增表与原始证据，回退应用时不重发订单、不清除未决身份；说明旧应用可能恢复原有延迟。不可逆删除或重写历史不属于回退步骤。

## Open Questions

无影响需求范围或方案方向的待确认业务问题。具体 SQL 批量大小与单片时间预算在实施时按现有容量配置和隔离测量确定；这属于内部调优，不改变当前动作准入或错误含义。原约 883 秒在锁等待/历史扫描/当前依赖读取间的精确占比仍缺现场分段证据，后续计时用于验证，不将推断写成已测结论。
